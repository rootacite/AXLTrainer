# 一块多出来的内存

**gfx1201 的 bf16 越界读，和一场持续数月的追查**

这是什么。一篇叙事，讲的是一块 AMD RX 9070 XT（gfx1201）显存里发生过的事，以及我为了把它搞明白走过的弯路：从"是不是桶的尺寸没对齐"，到"这是 ROCm 出厂预编译 kernel 在读它不该读的地方"，到"改源码这条路走不通"，到"那就不修 kernel 了，给它一块合法的地方去读"，最后到"等等，为什么同一个进程有三本账，而且它们能差出 2 GiB"。

这不是什么。它不是权威记录。权威记录是下面这几份，本文出现的每一个数字，我都标了它出自哪份文档的哪一节：

一句话结论。gfx1201 上，hipBLASLt 派发的 bf16 Tensile kernel 会读出 A/B 操作数的末尾；幅度不超过 4 KiB，读到的值不进入结果，操作数末尾之后如果是已映射内存，这件事完全无声——但只要那里是一页没映射的显存，GPU 就报页错误，进程当场被杀（-6）。这个读从 kernel 一侧修不掉，所以我换了个方向：不去堵那次读，而是让它读到的地方有内存可读。

## 第一幕 · 我以为是对齐问题（后来证明不是）

> 时间：几个月前。证据：[`../fixes/fix1.txt`](../../fixes/fix1.txt)

最初的症状很朴素：训练跑着跑着，进程会毫无预兆地硬崩一次。

```
IOT instruction (core dumped)
amdgpu 0000:03:00.0: [gfxhub] page fault (src_id:0 ring:24 vmid:8 pasid:144)
GCVM_L2_PROTECTION_FAULT_STATUS:0x00801031
Faulty UTCL2 client ID: TCP (0x8)
RW: 0x0
```

当时我的推理链是这样的，而且**每一步单独看都挺合理**：

1. **VAE 陷阱。** 图像被 VAE 压缩 8 倍（`f8`）。`bucket_step = 64` 时，有些桶会给出"是 8 的倍数、但不是 16 的倍数"的 latent——比如桶 `832×448` 给出 latent `104×56`。
2. **ROCm 更挑剔。** 跟 CUDA 生态比，AMD 的 ROCm（尤其 MIOpen 与 Flash-Attention 的 kernel）对非 16 字节对齐的维度**很不宽容**。
3. **于是越界了。** GPU 的 wavefront 对着这些没对齐的 latent 矩阵做向量化 load 时，指针偏移算错，读出界了。
4. **`shuffle=True` 解释了"随机"。** 每个 epoch 批次顺序都会变；连续几个"有毒"的桶如果撞上一个碎片化严重的分配器，就炸了。

对策看起来顺理成章：我把 `bucket_reso_steps` 从 **64 改成了 128**。这样 `128 ÷ 8 = 16`，latent 维度永远能被 16 和 32 整除。我在结论里写的是"训练顺利通过了所有早期瓶颈（step 5、25、40），跑完了 **1200+ 步**"。

这个改动留下来了（它确实是个真实存在的对齐约束，今天的仓库仍然要求 bucket_reso_steps = 128）。但"它能解释那次崩溃"这个结论没有留下来。

后来它被推翻了。今天的仓库文档在这一点上说得很直接：fix2.txt 写着"这不是 fix1 的桶 bug"，fix2-ex.md 又复述了一遍——bucket_reso_steps 本来就是 128，latent 是 96 × 128（kanae）或 96 × 160（另一套数据），都能被 16 整除，照样崩。而在我手上的全部材料里，fix1.txt 是唯一一份没有日期、没有 run id、没有 config 快照的结论——它靠的不是证据，是记忆。这次的教训很简单，也值得放在最前面："跑通了 1200 步"不等于"我修好了它"，也可能只是那 1200 步恰好没抽中下下签。

（有意思的是，它的 dmesg 家族和我后来抓到的**长得一模一样**：同样是 `[gfxhub] page fault`、同样 TCP client、同样 `RW: 0x0`。只有 ring 号不同——`ring:24` 对 `ring:157`。一开始，我对着正确的日志，读出了一个错误的结论。）

## 第二幕 · 越崩越像有规律，直到那个规律也被推翻

> 时间：2026-09-14（fix2）、2026-09-15 → 09-16（fix3）。证据：[`../fixes/fix2.txt`](../../fixes/fix2.txt)、[`../fixes/fix2/README.md`](../../fixes/fix2/README.md)、[`../fixes/fix2-ex.md`](../../fixes/fix2-ex.md)、[`../fixes/fix3/README.md`](../../fixes/fix3/README.md)

### 2.1 第一个像样的假说：partial tile

把栈换到 `torch 2.13.0+rocm10.0.0` / HIP `7.15.26333` 之后，崩得更勤了。`fix2.txt` 给出了一个精确得多的假说：**这是 Tensile 的 partial tile 问题**。

推理是这样的：PEFT LoRA 在 UNet 的 to_k/to_v 上对 encoder hidden states 求梯度时，会出现 [B · 231, 36] @ [36, 2048] 这样的 GEMM（K = network_dim）。取 B = 2 时 M = 462 = 7 × 64 + 14、K = 36 = 1 × 32 + 4——两个方向都是带余数的 tile。于是"gfx1201 的 MT64x64x32/64 kernel 在 global_load_tr 上丢掉了余数边界检查"。它给出的规避建议是：别同时用 train_batch_size = 2 和 network_dim = 36。

然后它被同一个实验包里的数据自己打死了（../fixes/fix2/README.md）：

- 那个"必崩组合"在真实的 188 张图数据集上**跑满了一个 epoch**（94 步，118 秒）。把每一句 caption 都补齐成 3 个 chunk，让每一步都满足 `M = 462`、`K = 36`——**还是跑满**。
- 它的前提在这批数据上根本够不着：caption 的 chunk 大小是 `tokenizer.model_max_length - 2 = 75`，而这批 caption 最长 **145** token，最多 2 个 chunk。batch = 2 时 `M` 只能是 154 或 308，**永远到不了 462**。
- 最狠的一下是 `network_dim = 32`：`K = 32` 恰好是一整块 32 宽的 tile，**根本没有 partial K tile**——它在 step 4 就崩了。

于是"避开 partial tile"作为一条规则被判死，理由只有一句：**同样的形状在一个干净的进程里跑得好好的。**

`fix2.txt` 里真正值得留下来的，反倒是它排除掉的那些：`PYTORCH_NO_HIP_MEMORY_CACHING=1` 能撑过 5 步（代价很大，见下），而"把 TE 的 backward 和 UNet 的分开"、`TORCH_BLAS_PREFER_HIPBLASLT=0`、"只用 math 的 SDPA"、"关掉 TE checkpointing"——**全部无效**。

### 2.2 九月十四号那一夜：6/6

真正的转折出现在 2026-09-14 晚上。同一份配置，只改 seed：`seed = 1145141920` **连续 6 次崩在 step 101**；`seed = 1145141919` 跑了 7 次，7 次都活。

内核日志里的四条（同一晚，四个不同 pid）：

两个细节我当时就记了下来，后来全用上了：两次尝试的 rptr/wptr 完全相同（3353460 / 3353739），但故障地址不同；而所有故障地址都是 2 MiB 对齐的。

seed 这件事的机制我先摸清了一层：`shuffle_caption` 的随机数取自 `cfg.seed + epoch + sha1(image_path)`，所以 tag 顺序（进而分词后的 chunk 数，进而这个 LoRA GEMM 的 `M`）依赖 seed。两个 seed 的 `M` 直方图：`{462: 102, 231: 18}`（活的）对 `{462: 101, 231: 19}`（死的）。第一步出现差异是在 step 96，而**死的那一步（101）恰好是一次 462 → 231 的形状切换**。

看着挺像那么回事——但我很快意识到这个解释站不住脚，而它站不住脚这件事，反过来定义了后面所有的实验设计：

> 形状本身不足以解释：`M = 462` 占了两个 seed 大约 85% 的批次，两个 seed 绝大部分时间都待在里面。真正不同的是**序列**，而崩溃恰好落在一次**形状切换**的步骤上。同时，布局是可复现的——因为形状序列由 seed 固定，分配器的排布也跟着被固定，这就是为什么同一个 step 每次都失败。

### 2.3 决定性的一步：把采样关掉

如果"形状切换"是原因，那只要让序列里没有切换就行——可那样就没法正常训练了。于是我干脆把**采样**关掉了（`save_every_n_steps = 0`）：

同一份 seed、同一批形状、同一个优化器，这次跑满了 120/120 步。原来是采样这一段，把分配器推进到"越界正好落在未映射页上"那个状态里。

于是我对整件事的说法改了：

形状告诉你在哪里越界；真正决定那一下会不会踩空的，是周围的分配布局——具体到一次真实训练、一个特定的 step、一个特定的 seed。

同一份证据还顺手给出了一张阶梯（同一 seed、同一形状，只动采样节奏）：

| 采样节奏 | 死在哪 |
| --- | --- |
| 每 30 步，768×768 样本 | step 101 |
| 每 30 步，512×512 样本 | step 90（第 3 个样本那一步） |
| 每 30 步，样本只降噪一步 | step 90（同一步） |
| 每 10 步，512×512 | step 31（第 3 个样本之后一步） |
| 每 5 步，512×512 | step 20（第 4 个样本） |
| 每 2 步，512×512 | **step 8**（第 4 个样本） |
| 每 3 步，512×512 | 活着（12 步、4 个样本） |
| 每 30 步，256×256 单步样本 | 活着 120/120（这么小的样本什么也污染不了） |
| 关掉 | 活着 120/120 |

这张表可以读出两条：死亡集中在"第 3 或第 4 个样本上，或紧随其后"；**把样本改小是把失败推早，不是推没**。另外还有一条很干净的边界：`flush_memory_every_step`（每步 `empty_cache`）**不管用**，`max_data_loader_n_workers = 0` 也**照死不误**——所以 DataLoader 的 forkserver 可以从嫌疑名单里划掉了。

### 2.4 一连串"最小复现"全灭

这一节是我花掉最多算力、拿到最少正面结果、但价值最高的一节：**我把能想到的"更小的复现"都写了一遍，它们全部活着。**

| 夹具 | 它做什么 | 结果 |
| --- | --- | --- |
| `crash.py` | 自带一个 dim-32 的训练循环（不 import `trainer/`） | 8/8 步活着，跑三次都活；损失值和真训练器**对得上**（`0.1498 / 0.1525 / 0.1633 / 0.1219` 对 `0.1498 / 0.1524 / 0.1632 / 0.1219`），`AMD_LOG_LEVEL=4` 显示两者碰的是**同样的 67 个 Tensile kernel**，第一步的 5735 个分配尺寸也**一一相同** |
| `repro.py` + `trial.py` | 无模型：真 PEFT LoRA GEMM，扫 M / rank / dtype / 分配器扰动 / 层数 / 常驻量 | **0 / 40** 崩 |
| `repro_unet_sweep.py` | 真 SDXL UNet + LoRA，真桶 latent | **0 / 7** 崩 |
| `repro_joint.py` | 真 UNet **和**两个 CLIP 文本编码器一起 backward（`fix2.txt` 说这个组合必崩） | M=231、M=462 都活着 |
| `repro_min.py` | 独立 diffusers + peft + torch 循环 | 5 种变体，**没有一种崩** |

这一节可以压成一句话：**这个 fault 是这个进程分配历史的属性，不是这一步本身的属性。**

顺手也把环境变量这一层测清了（12 步窗口，同一份 latent 缓存）：

| 变量 | 结果 |
| --- | --- |
| 什么都不设 | step 4 崩 |
| `HSA_SVM_GUARD_PAGES=0` | 活着 12/12 |
| `PYTORCH_NO_HIP_MEMORY_CACHING=1` | 活着 12/12 |
| `GPU_SINGLE_ALLOC_PERCENT=50` | step 4 崩 |
| `HIP_MEM_POOL_SUPPORT=1` | step 4 崩 |
| `HSA_DISABLE_FRAGMENT_ALLOCATOR=1` | step 4 崩 |
| `HSA_DISABLE_CACHE=1` | step 4 崩 |
| `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` | 第一步 loss 就是 `NaN`，训练器连序列化都过不去（不能用） |

关于 HSA_SVM_GUARD_PAGES=0——它在后面的故事里反复出现，这里先定位清楚：它不是修复，它关掉的是探测器。ROCm 默认在 SVM 分配后面留一页不映射的 guard page（那个变量默认是 1），关掉之后，越界读落在已映射内存上、静默读完，什么事都没有。它在这次追查里是极好的探针（正因为关掉它之后损失和 LoRA 张量逐字节不变，我才敢断言"这次读本身是惰性的"），但它永远不该出现在生产环境：它会把这个进程里每一次越界读都一并变成静默行为。

`PYTORCH_NO_HIP_MEMORY_CACHING=1` 是另一回事：它让每个张量各自去要一次 `hipMalloc`，于是没有哪个操作数正好卡在缓存段的边缘。有效，但慢 2.2–2.9 倍（2.9 s/it 对 1.12 s/it），而且它改的是全局的分配器行为。**这是缓存，不是修复。**

### 2.5 关于"逐字节不变"，以及我差点骗过自己

我做了一次完整性对照：`cached` 对 `no-hip`（seed 1145141919）**120/120 步损失逐字节相同、2208 个 LoRA 张量在 step 30/60/90/120/final 全部逐字节相同**；dim 32 的 12 步对照同样全等；甚至那个"崩在第 101 步"的运行与活下来的运行，**在它们共有的 101 步里损失与张量全部相同**。

（同一批实验也暴露了两个坑，都记在案：**两次同配置的运行不会得到相同的 latent 缓存**——6 个 latent 里只有 1–4 个能和另一次对上，因为 MIOpen 每次进程会挑不同的卷积算法，所以任何"逐字节对比"都必须在固定缓存的前提下做；以及**第一版 seed 网格的种子只写在行标签里、没真正传进行里**，制造出一个"换个样本 seed 就能把活的变成死的"的漂亮结果，纯属标签错误，后来被 `repro_real.py` 用"标签里的 seed 和实际要跑的 seed 不一致就拒绝启动"堵死。）

### 2.6 然后它把第一步也吃了：fix3

> 时间：2026-09-15 23:16 → 2026-09-16 00:30。证据：[`../fixes/fix3/README.md`](../../fixes/fix3/README.md)

`fix2` 那套实验是在 `2.13.0+rocm10.0.0` 上做的。为了对照，我把栈改回 `2.12.0+rocm7.14.1`——然后发现**打包好的 fix2 复现包在这套栈上不崩了**，我自己线上那份配置也顺利跑了 700+ 步。

我差点就把"回退栈"当成答案了。

fix3 做的事是：**拿仓库里 commit 的那份 `config.toml`（`network_dim = 48`、`train_batch_size = 2`、640 张图）在这套栈上跑一遍**——结果它**死在第一个训练步，每一次，约 15 秒**。改了 seed 也一样（seed 1145141919：9 次 9 崩，`steps_reached` 全是 0）。重启后依旧。

于是 `doc/troubleshooting.md` 里"这套栈免疫"的说法被我撤回：它改变的只是**抽签中不中**，而不是**kernel 会不会越界**。

fix3 最有价值的产出是 `probe_op.py`：它把自己塞进训练器的位置，把每一步启动的每个 GEMM 连同形状、forward/backward 标签都记下来。崩溃前最后一行是：

```
OP 8344 backward aten.mm.default [[48, 308], [308, 1280]]
Dispatch Header = 0xd02 (type=2, …), setup=3
grid=[2560, 1, 1], workgroup=[128, 1, 1], group_seg_size=1638
Memory Fault Error … faulting addr: 0x7f2d68800000,
  kernel: Cijk_…_MT64x128x16_…_ISA1201_…
```

这是**文本编码器 LoRA 的 A 权重梯度**（`grad_A = grad_outᵀ @ input`），它的三个维度各有身份：`M = 48 = network_dim`（秩）、`K = 308 = batch(2) × 序列长(154)`、`N = 1280 = text_encoder_2` 的 hidden size。同一步的上下文是 `8331 lora_A input grad` → `8332 grad_A`（死在这里）→ `8333 lora_B input grad` → `8334 base layer input grad`。

fix3 还做了一件很有说服力的事：它把桶和这一步的 GEMM 分开测了。

| 桶 | latent | batch 2 时的 `M` | rank 24 | rank 48 | rank 64 |
| --- | --- | --- | --- | --- | --- |
| 1280 × 768 | 160 × 96 | 308 | ok | 崩 | ok |
| 512 × 1920 | 64 × 240 | 308 | ok | 崩 | ok |
| 512 × 2176 | 64 × 272 | 308 | 崩 | 崩 | ok |
| 1408 × 768 | 176 × 96 | 462 | ok | ok | ok |

关键在于：**桶根本不出现在这个 GEMM 里**。文本编码器只看 `batch × sequence`，它从来看不见图像。所以桶只可能通过分配器起作用——UNet 为这个桶分配的激活量决定了文本编码器那些 LoRA 缓冲会不会正好贴着一个空洞。（`M = 308` 本身也不充分：`(1280x768, 24)`、`(1280x768, 64)`、`(512x1920, 24/64)` 和致命的格子行数相同，却活着。）

46 次 fault 里 **44 次是同一个 855 字符的 kernel 名**，两次例外是 `network_dim = 36` 落在另一个解法（`MT64x64x64`）上。没有一次崩溃发生在 `M = 154` 的步骤上。

## 第三幕 · 把 PyTorch 整个扔掉，自己写一个复现

> 时间：2026-09-15 夜 → 09-16 凌晨。证据：[`../fixes/hip1/hip1.md`](../../fixes/hip1/hip1.md)、[`../fixes/hip1/source-trace.md`](../../fixes/hip1/source-trace.md)

到这一步，"是我自己代码的问题"这个可能性还很大：也许是 torch 的缓存分配器，也许是我的数据集/掩码/循环，也许是 MIOpen 选了个坏算法。

于是我决定把整个 PyTorch 栈剥掉，直接写一个 HIP 程序（`fixes/hip1/launch_fault_kernel.hip`）去复现它。这个程序的做法很直接：

1. 从磁盘取 hipBLASLt 自己装着的那份 code object（把一个 `.co` 文件用 `clang-offload-bundler` 解开，得到里面的 ELF），**整个进程只加载这一个文件**；在这个文件里只查**一个** kernel，名字就是源码里那个 855 字符的字面量。
2. 手工搭那 144 字节的参数块（`static_assert(sizeof(Args) == 144, "the metadata says kernarg_segment_size is 144")`），走 `hipModuleLaunchKernel` 的 raw-buffer 形式（hipBLASLt 自己也是这么发的，ABI 布局由我来定，而不是让 runtime 去猜）。
3. **给操作数摆好位置**：每个操作数用 VMM 预约 `mapped + 4096`，映射 `ceil(size/4096)×4096` 字节，然后**把 kernel 要用的那块放在映射的末尾**——于是操作数的最后一个字节就是映射的最后一个字节，紧跟着的那页预约了但从不映射。**只要越过边界，就必然撞上它。**

这个实验的结果直接决定了后面的研究方向：**一个单进程、没有 torch、没有 hipBLASLt、没有 MIOpen、没有数据集、没有分配器邻居的程序，照样当场崩了。**

因为怀疑可能是我自己搭的那个参数块有问题，我又走了第二条路线（`launch_fault_via_rocblas.hip`）把这个变量也去掉：直接用 `rocblas_gemm_ex` 调 `m 1280 / n 48 / k 308`，让库自己去选解法（它选了 `sol-idx = 107020`），同样把操作数摆在页边界上——**fault 落在 B 那块 29,568 字节操作数的 guard page 第一个字节上**。

这两条路线一共留下三条独立证据，把责任钉死在"库自己那份预编译 kernel"上：

（一）eBPF 看到的加载链（6 个 uprobe；这里有个坑：进程的线程名是 pt_autograd_0，按 comm == "python" 过滤会什么都看不到——我头两次尝试就是这么白跑的）：

```
hipModuleLoad        comm=pt_autograd_0  file=…TensileLibrary_BB_BB_…_l_Ailk_Bjlk_…_gfx1201.co -> err=0
hipModuleGetFunction … err=500 (hipErrorNotFound) ×4  → … err=0
hipExtModuleLaunchKernel … grid=2560,1,1 -> 488 dispatches
```

这是 hipBLASLt 的懒加载模式：先问所有已加载的模块有没有这个 kernel，都没有才去加载那个有的文件——**所以这个 `.co` 在运行中很晚才出现，而且只出现一次**。（后来的单位修正：`grid=2560,1,1` 是 work-item 数，等于 20 个 workgroup。）

（二）故障日志自己带证词。ROCr 的 dump 里有 kernel_obj，也就是硬件执行的那个 kernel 描述符地址；描述符的虚地址是 0x282380，四次记录的差值全是 2 MiB 对齐：

| 运行 | `kernel_obj` | 减去 `0x282380` |
| --- | --- | --- |
| fix3 实跑（2026-09-15） | `0x7f2cd2682380` | `0x7f2cd2400000` |
| eBPF 第 2 次 | `0x7f3f92082380` | `0x7f3f91e00000` |
| eBPF 第 4 次 | `0x7f77f5882380` | `0x7f77f5600000` |
| hip1 单进程复现 | `0x7f8556a82380` | `0x7f8556800000` |

最后一行是最有说服力的证据：**一个只加载过这一个 code object、只发射过这一个 kernel 的进程，仍然崩在同一个描述符上。**

（三）排除法。rocBLAS 自己那份 gfx1201 懒加载库里 "solutions": []，它的 67 个 code object 里没有一个含 Cijk_/UserArgs 字符串；MIOpen 的缓存里也没有这个名字（它的 kernel 叫 Im2d2Col_v2 / batched_transpose_*）；torch/torchvision 的包里同样没有。而且这不是 JIT 或缓存的产物——这个名字在 run 开始之前就已经躺在出厂 .co 里，运行只是读了它。

顺手把影响面也数了一遍：gfx1201 上 hipBLASLt 装的 4 个纯 bf16 Tensile 库，解出来 **2105 个 kernel，1830 个可以发射**（275 个被跳过，原因清一色是 `globalSplitU > 1`，需要 split-U 工作区），按布局分 372 / 406 / 303 / 749。另一条独立路线（`sweep_gemm_shapes.hip`，让 hipBLASLt 自己选解法、扫形状）跑出 **234 次 fault、覆盖 15 个不同 kernel，全部落在两个 `Bjlk` 布局的库文件里**。

单看那一个 kernel 的形状阶梯（围绕它自己的 macro tile 造的 10 个形状，pad 0）：clean 4 / wrong 0 / fault 6——唯一干净的是那个"正好填满 tile"的形状（128 × 256 × 64，K = 4 × DepthU，crc 0xe4a70c8f）。距离梯子只有三行：

| `--pad` | 结果 |
| --- | --- |
| 0 | **崩**（落在 B 的 guard page 第一个字节；B = 64×308 = 39,424 字节） |
| 4096 | 干净，crc `0x4ec0d5e7` = 精确参考值 |
| 65536 / 262144 | 干净，crc 同上 |

越界超过 0 字节、不超过 4096 字节，而且读到的数据不改变 D。（fix2 时期的数值口径是"最多 4 KiB 越界，杀死训练的那个形状算下来是 2 KiB"。）

## 第四幕 · 为什么这次越界读是躲不掉的

> 证据：[`../fixes/hip1/source-trace.md`](../../fixes/hip1/source-trace.md)、[`../conclusions/bf16-kernel-overrun.md`](../../conclusions/bf16-kernel-overrun.md)

这一幕的结论其实一句话就能说完：**只要矩阵的行是紧密排列的，读到原本不需要的东西就躲不掉；真正的问题只是多读的地方合不合法——而实验说明，它完全可能不合法。**

### 4.1 读是必然的

我把那个 kernel 反汇编了一遍：一共 120 条 load，其中 **36 个是 `global_load_tr_b128`**（每次 16 字节的转置 load），分布在 4 个位置（每个 9 条）——**这个 kernel 对 A/B 操作数的每一次读取，都是 16 字节的向量化转置 load**。而这 4 个位置里**只有最后一个**前面有边界钳位：

```
0x56FFF0  v_min_i32_e32 v64, v148, v64                 // 钳位
0x56FFF4  global_load_tr_b128 v[76:79], v64, s[48:49]  // A，16 字节
0x570060  v_min_i32_e32 v65, v148, v65
0x570064  global_load_tr_b128 v[84:87], v65, s[52:53]  // B（×8）
```

（打进来的形状是 `M = 48`、`N = 1280`、`K = 308`。`K = 308 = 19×16 + 4`，所以最后一块尾 tile 一定要取进来；`M = 48 < 64` 的 macro tile，所以第 48…63 行也会被取进来。）

这三处越界各自的量级：

| 位置 | 为什么 | 最坏情况 |
| --- | --- | --- |
| A 的 K 尾 | `K = 308 = 19×16 + 4`，最后一行要取 l = 308…319 | 12 个元素，**24 B** |
| A 的 M 边 | `M = 48 < MT64`，i ≥ 48 的行也被取 | 16 行，**9.6 KB** |
| B 的 K 尾 | B 是 `[K,N]` 存储，l = 308…319 是整整 12 行越界 | **30 KB** |

实测：hip1 的单进程复现崩在 **A 的映射末端之后的第一批页**里（6 次重复里 5 次落在 guard page +4096、1 次落在 guard page 本身；`M` 边的越界跨度是 9,856 B ≈ 2.4 页，ROCr 报的是 warp 先撞上的那一页）。rocBLAS 那条路线（库自己的描述符，m=1280/n=48）算下来最远读到 158 字节，落在第一页里。**所以可以复现的断言只能是"操作数末端之后、头几页之内"。**

### 4.2 ISA 保证不了合法

生成器**知道**自己在越界读，而且它认为这是"被允许"的——只要下面这条假设成立：

```
asmCaps["HasPartialOOB"]   # KernelWriterAssembly.py:10214-10215
```

而 `hardware_caps.hpp:96` 把它定义成"**除了 gfx1250 之外的所有 ISA**"：

```
checkNotInList(isaVersion, {{12,5,0}})
```

gfx1201 在这个列表里，所以生成器认为"超出边界的那部分访问会被硬件丢掉"，于是它敢发这条宽 load，还**专门预先把目标寄存器清零**（生成器注释原话：`set to zero to avoid unexpected value`）。

但这个假设要靠描述符来承载，而这条路径上的描述符没有 bound 字段。一个 MUBUF 的 buffer_load 有记录数（record count），硬件可以据此裁掉越界部分；而这里用的 global_load_tr_b128 只有 2 个 SGPR 的 64 位地址操作数，没有任何 bound 字段——在这条路径上，没有任何东西在执行那条假设。

这就是"ISA 保证不了合法"的确切含义：**ISA 的能力声明是有条件的，而条件没被满足，也没被检查。**

### 4.3 kernel 也保证不了

那 kernel 自己呢？它唯一的保险就是上面那条 `v_min_i32`，出自生成器的 `KernelWriterAssembly.globalReadGuardK`（`:10207`），注释写着：

```
"truncated load: clamp GRO to legal range"
```

它的三个性质，每一个都致命：

1. **它钳的是地址，不是访问窗口。** `VMinI32(offsetVgpr, maxGroVgpr, offsetVgpr)` 限制的是这次 16 字节访问**从哪里开始**；访问宽度压根没进这个计算。所以一个"关于最后一个元素是对的"的上限，仍然允许这次访问结束在它之后**最多 14 字节**。
2. **上限来自问题的 K 余数与 tile 几何，不来自操作数的大小。** 那段 `isTr` 代码里**没有任何一处**提到"分配了多少字节"。
3. **越界的数据是事后丢弃的，不是事前避免的。** 尾循环里 `v_cmp_ge_i32 s66, v149, s12` 拿 K 边界比一下，`v_cndmask_b32_e64 …, 0, s66` 把寄存器换成零——**可是读已经发生了**。

所以呢？**kernel 只是个算数的，它没法凭空给用户变出一个合法页框。**

### 4.4 三个"修生成器"的候选，全部实测失败

我真的写了三个候选补丁去改那段钳位，跑了那套 10 形状阶梯：

| 候选 | 做什么 | 结果 |
| --- | --- | --- |
| A | 上限再减一个访问宽度（14 B） | 训练器那个形状 CLEAN，**但阶梯上 10 例里 7 例算错** |
| B | 超过上限的读改成读块首 | 仍然 fault（10/10 干净，crc 精确——但"读块首"这个语义本身是错的） |
| C | 上限 = min(现在, 操作数剩余字节 − 一个访问) | CLEAN，**同样 7/10 算错**，且 crc 与 A 相同 |

原因写出来很朴素，也很根本：**那些跨过操作数末端的读，有一部分是在界内的，而界内那部分是尾块真正需要的数据。** 所以这次访问**既不能收窄**（会丢掉需要的数据）**也不能封顶**（地址侧封不住宽度）。生成器补不了这个洞。

`source-trace.md` 用一句话给这一节收尾，我认为那是整份材料里最重要的一句：

要么操作数自带余量，要么这个解法不该被选中。

这正是后面所有工作的分界线；我后来选了前半句。

## 第五幕 · 改源码这条路，走不通

> 证据：[`../fixes/hip1/gltr-asem-rule.patch`](../../fixes/hip1/gltr-asem-rule.patch)、[`../fixes/hip1/hip1.md`](../../fixes/hip1/hip1.md) §13

生成器那侧的钳位补不上，我就顺着"要么这个解法不该被选中"这句话往下走：**用厂商自己的机制，把会越界的解法排除掉。**

厂商确实有这么个机制。ROCm 源码里有一行现成的惯例（注释写着"用 `AssertSummationElementMultiple`（在谓词里就是 `BoundSizeMultiple`）排除失败的 tail-loop 情形"）：

```
state["AssertSummationElementMultiple"] = max(state["AssertSummationElementMultiple"], state["DepthU"])
```

它本来只用在两种布局上；我把它扩到了 GLTr 布局（`Solution.py`，10 行）：

```
    if state["enableGLTrA"] or state["enableGLTrB"]:
        state["AssertSummationElementMultiple"] = max(state["AssertSummationElementMultiple"], state["DepthU"])
```

补丁头的注释我写的是：`实测：它把选择从 DTV 解法上移开了，但没有止住崩溃`。测量结果：

- 这个家族 473 个解法里，**157 个被改名**（各自的 `ASEM` 变成自己的 `DepthU`）。
- 运行时**确实**不再选 DTV 解法了（日志里 `…ASEM1…DTVA0_DTVB1` 变成 `…ASEM1…DTVA0_DTVB0…`）。
- **但崩溃没有消失：12/12 全部 fault**（4 种 epilogue 变体 × 3 种库配置：出厂版、重建无谓词版、重建加 `BoundSizeMultiple` 版）。
- 原因也看清楚了：**被改名的那个 kernel 仍然有 36 条转置 load 和 5 个 tail 标签**——`ASEM → NoTailLoop` 并没有把那次被钳位的读去掉。也就是说，这个家族**至少有两个 over-reader**：DTV 的，和替补上来的非 DTV 那个（后者用 1 元素的 `buffer_load`，越界的方式和 GLTr 的钳位无关）。

另外还有一个更结构性的理由，说明这条路走不通：这条规则要拒掉这个家族 473 个解法里的 157 个，而厂商自己的调优表里，它覆盖的 7768 个问题没有一个受影响——其中 6345 个由 DTV 解法拿下，而这些问题的 K (mod DepthU) 全部为 0。换句话说：会崩的这个形状，从来没进过厂商的 benchmark 集。这也顺便解释了为什么它从来没被调优掉。

至于部署，就算这条规则有效，代价也很硬：

- 运行时装的是**预编译的 `.co`**，所以必须重建，而且 `.co` 和 `.dat.zlib` **必须一起换**（运行时按 `.dat` 里的名字选 kernel，参数块描述也在同一条记录里）。
- 部署要靠 `HIPBLASLT_TENSILE_LIBPATH` 指向另一棵库树，而它**必须指向"装着那些文件"的那一层目录**（loader 会把文件名拼在后面；指到上一层，hipBLASLt 直接回 `HIPBLAS_STATUS_INVALID_VALUE`；指到一个不存在的路径，日志里会出现 `hipModuleLoad failed: /nonexistent/Kernels.so-000-gfx1201-xnack-.hsaco`）。
- 源码在仓库外的一个 checkout 里，改的是**一个文件**（外加两个必须的 untracked 符号链接）。
- 单文件重建（427 个 kernel）要 **15 秒**，重建保真度没问题（427 = 427，未改动的重建能在同一个地址上复现同一个 fault）——**但性能代价一次都没测到**：凡是被这条规则改掉选择的形状，都先崩了，运行根本活不到打时间行。

结论：**Patch 源码这条路径的可行性极低，我不打算走它。**

> 一处更正：这份材料的早期版本里写着"这条规则确实去掉了越界读（10/10 无 fault）"。那句话不成立——当时那个 build 同时还带着候选 C 的生成器实验，零 fault 是候选 C 带来的，与这条规则无关；把生成器恢复成原版之后，改名后的 kernel 在同样那六个形状上照样 fault。这句话已经撤回。

## 第六幕 · 换个角度：别修 kernel，给它一块合法的地方去读

到这里，我对整件事的认识是这样的：读是必然的，合法性没人保证，而修 kernel 那条路被三件事同时堵着——**钳位补不了、解法躲不掉（家族里至少两个 over-reader，而厂商的调优表里根本没有这个形状）、重建加部署的成本与风险都不可控。**

于是我把问题重新表述成了一句人话：

既然不能让 kernel 别读，那就让它的读落在一块存在的内存上。

这句话展开是两个方向：

方向一：ROCm 架构层。这条路要求 ROCm 自己保证：会参与这类指令运算的内存，尾部一定存在这样一个合法空间。而这恰恰暴露了当前 ROCm 内存管理体系的一处架构缺陷：guard page 是它自己设计进去的（HSA_SVM_GUARD_PAGES 默认 1），2 MiB granule 的取整也是它自己的规则——一个"整颗 granule 刚好用完"的分配，它的下一个字节就是未映射页，系统里没有任何一层承诺过要给这种分配留余量。要在这条路径上把事做对，就得动内存管理架构本身：要么让分配器在尾部保留一页，要么让这类指令的语义在驱动层被兜住。这大概也是 AMD 迟迟没解决它的原因——这不是一个补丁能搞定的，这是一次架构手术。

方向二：调用方层。我在申请内存的时候就多要一个保留页，这是投入产出比最高的一条路：不需要任何人批准，不需要动 ROCm，也不需要动 kernel，只要在"内存交出去"和"kernel 拿到它"之间的那一层加一句话。我选了这一条。

动手之前，有两种实现方式摆在面前：

| 方式 | 好处 | 代价 |
| --- | --- | --- |
| 改 torch 的内存池代码 | 从源头解决，一次做完 | 要维护 torch 的分支/补丁，跟着上游升级；只覆盖 torch 的分配路径 |
| **二进制 hook（`LD_PRELOAD`）** | 不碰 torch、不碰 ROCm、不重新编译任何东西，可随时开关 | 只拦得到跨 PLT 的调用；属于外部工具 |

我选了后者。于是有了 **amdfq 计划**——这个名字的来历就不翻译了，全称是"全程 AMD FUCK YOU"，缩写正好是这四个字母。冷静下来看，这个名字记录的是我当时的情绪：**我认输了，但认得还算有点尊严——我不再试图让 AMD 的 kernel 变对，而是把它围起来。**

## 第七幕 · 一个 16 字节的补丁，和证明它真的有用的控制组

> 时间：2026-09-17。证据：[`../amdfq.md`](../../amdfq.md) §9–§10

第一版补丁小得可以贴在名片上：`hipMalloc` 向 runtime 多要 **16 字节**，然后把原来的指针还给调用方。

```
hipError_t hipMalloc(void **ptr, size_t size) {
    size_t padded = size <= SIZE_MAX - 16 ? size + 16 : size;
    hipError_t result = real(ptr, padded);   /* 调用方仍然只看得到 size */
    ...
}
```

为什么 16 字节就够了，这里有个不太直观的地方。真正起作用的不是那 16 字节本身，而是 runtime 的 2 MiB granule 取整：一个请求量恰好是 granule 整数倍的分配，本来会正好用光它那一颗 granule、下一个字节就是未映射页；加上 16 字节之后它装不下了，runtime 只好再 reserve 一整颗 granule 给它。于是那个边界后面多了一整颗 2 MiB 的已映射内存（地址空间和显存都有）。代价就是这一整颗。

`hipFree` 不需要知道这些（它只拿指针），所以调用方一侧完全无感：同一个指针、同一个 size、同一份布局。

### 7.1 控制组：证明是 pad 起作用，不是装了这个钩子本身

一个 `LD_PRELOAD` 对象本身就会改变分配布局，所以我必须把"插桩"和"加 pad"这两件事分开，做法是做一个只差**一行**的构建（`AMDFQ_VRAM_PAD 16 → 0`，`diff -r` 确认那一行以外没有别的）：

| 运行 | 预加载 | pad | 结果 |
| --- | --- | --- | --- |
| `lllj_20260917_041147` | — | — | step 10 abort；`[gfxhub] page fault` 04:12:31，pid 71023 |
| `lllj_20260917_045346` | — | — | step 10 abort；fault 04:54:10，pid 85072 |
| `lllj_20260917_050031` | `libamdfq.so` | 16 | 14 步，无 fault，手动停 |
| `lllj_20260917_050412` | `libamdfq.so` | 16 | **41 步，exit 0，`status=finished`** |
| `lllj_20260917_050950` | `libamdfq.so`（pad-0 构建） | **0** | **step 10 abort**；fault 05:10:16，pid 96771 |

最后一行就是控制组：**它插桩但不加 pad，于是照样崩**。另外三条证据把"巧合"这个选项也堵掉了：

- **同一份运行，不是相似的一份。** 控制组前 4949 条 `hipMalloc` 的尺寸与加过 pad 的那次**逐条相同**，从第 4950 条开始分叉——因为控制组那时已经死了。
- **速度没变。** 控制组 10 步的中位数 1.160 s/step，加 pad 那次 40 步是 1.154，无 hook 的一次是 1.159。插桩没有扰动时序。
- **同一个 fault 回来了**：同一个 step（10）、同一个签名（`0x00801031`、TCP client）、而且 abort 的运行**没有 `fini` 摘要**（进程被 `SIGABRT` 带走，不是干净退出）。

### 7.2 代价：贵，贵到不能接受

我从加过 pad 的那次自己的日志里重放了 malloc/free 流，按 `round_up(size + 16, 2 MiB)` 给每个活块记账：

| | 不加 pad | 加 pad | 代价 |
| --- | --- | --- | --- |
| 全run 峰值常驻 | 12,244 MiB | 14,778 MiB | **+2,534 MiB（1.207×）** |
| 稳态训练（15–55 s 的 5 s 窗口） | 11.2–12.2 GiB | 13.6–14.7 GiB | 中位 **+2.49 GiB** |
| 那一刻整卡用量 | — | 15,925 MiB / 16,304 MiB | **只剩 379 MiB** |

原因是 granule：**14,038 次 `hipMalloc` 里有 14,032 次要的是 granule 的整数倍**（其中 10,972 次是缓存分配器的 2 MiB 小池段）。峰值时刻大约 1,255 个块活着，1,255 × 2 MiB 就是那 +2.5 GiB。唯一不受影响的尺寸类是 25 MiB（6 次调用），因为它本来就没对齐。（累计字节数在这里没意义：整个 run 要了 172.15 GB，其中属于 pad 的只有 **224,608 字节**。）

这里要提前说一句：这 +2.5 GiB 是"这个进程还能用的显存"少掉的部分，不等于驱动计数器会涨的幅度。第八幕会说明后者只涨了 0.3 GiB 左右，以及为什么"少掉的 2.4 GiB"仍然是真金白银——至少对 ROCr 自己的客户而言。

时间成本几乎为零（1.154 对 1.159 s/step）。**但 +2.5 GiB 在 16 GB 的卡上是要命的**：峰值不在训练步，而在 run 末的 checkpoint 保存，那一刻离满卡只剩 379 MiB。

第七幕的结论可以压成一句：**机制成立，设计不合格。** 一个"每个活块买一颗 granule"的方案，价格是这张卡剩余的绝大部分余量。**价格必须降下来，怎么降，是后面两条路线的事。**

## 第八幕 · 内存到底去哪了

> 时间：2026-09-17。证据：[`../amdfq.md`](../../amdfq.md) §11、[`live-data.md`](live-data.md)（四轮的中文原始记录，663 行）

这一幕是我被自己骗得最惨的一段。

### 8.0 序：从一个孤立的小探针开始，怀疑起了账本

事情的起因很无辜：我想给"降价格"这件事定一个基线，于是先去量了一下 pad 到底花了多少钱。

第一步是最朴素的：写一个只做一件事的小程序（`probe_hold.c`）——申请 1024 个 2 MiB 的块，全部保持存活，同时读计数器、ledger、GTT、RSS。同一份二进制跑两次，唯一区别是有没有预加载 pad 库。结果非常干净：不带 pad 时，请求 2048 MiB，计数器和 ledger 都精确涨了 2048.0 MiB；带 pad 之后，两本账都精确翻倍涨到 4096.0 MiB。GTT 和 RSS 全程纹丝不动——**在这个孤立场景里，pad 的代价是真金白银的 2 GiB，账目分毫不差，两本账互相印证。**释放之后 0.25 秒内两本账都干净回到基线，没有任何残留。

我又怕这是"没有 torch 介入"的特例，于是把同样的思路搬到 torch 的缓存分配器上（`torch_hold.py`）：分配固定数量的张量并全部保持存活，不碰任何数据。这里冒出一个值得记住的细节——**`hipMalloc` 的调用数可以比张量数少一个数量级**。同样分配 1024 个 2 MiB 张量，经过 torch 缓存分配器只产生 **103 次 `hipMalloc`**（因为它一次抓 20 MiB 的段，再在段内切），而直接用 HIP 是 1024 次、每次 2 MiB。三组实验（HIP 探针 1024×2 MiB、torch 池化 1024×2 MiB、torch 1:1 的 500×20 MiB）全部**分毫不差**地验证了同一条规律：代价永远等于**存活的 `hipMalloc` 调用数 × 2 MiB**，跟张量数没关系，账目永远精确对上。

所以这套理论看起来已经很扎实了：只要知道训练里同时存活多少个 `hipMalloc` 块，就该能算出 pad 该多花多少钱。

然后我拿真实训练一测，理论直接崩了。同样的分配序列，带 pad 和不带 pad 的两次跑，计数器上的差别远远够不着理论值——模型算出来应该多花 1.5 GiB 左右，amdgpu_top 盯着看，实际差别小到可以忽略。而且这个落差不是采样噪声：我换了三种采样方式（4 Hz 轮询、压到 0.25 秒一桶、逐次全量对账），结论完全一样。

紧接着我一条一条排除了看起来最顺手的解释：不是采样太粗（三种采样方式结论一致）；不是计数器把 GTT 或主机内存也算了进去（探针里两边都监控着，纹丝不动）；不是"多出来的页框被后续分配复用了"（回放 25,850 次真实训练的 `hipMalloc`，返回指针全部 ≥2 MiB 对齐，没有一次落进任何多余页框）；更不是 torch 偷偷把那块多出来的内存拿去用了——这条我查得最狠：torch 的所有共享库里连 `hipMemGetAddressRange` 这个符号字符串都搜不到，它用来查询指针属性的结构体压根没有长度字段；HIP 的 API 自己也会拒绝越界的 `hipMemset`/`hipMemcpy`；最后我干脆写了个内核直接往那块多出来的页框里打哨兵、反复回读，几百个块、上千次校验，**改动字节数永远是 0**。这条路是彻底死透了。

pad 的大小本身也不是变量：16 字节到 2 MiB，五档几乎无法互相区分；只有当 pad 跨过第二个 2 MiB 粒度（2 MiB + 1）时，代价才会翻倍——这跟理论完全吻合，说明"取整到某个固定颗粒"这套账本身没错，错的是训练场景里这套账对不上。而且这个落差还有一个更诡异的地方：pad 的代价在加载阶段是看得见、也定量吻合的（此时存活块约 600 个，理论 1.2 GiB，实测 +1.1 ~ +1.3 GiB，对得很准）；可一旦进入正式训练步、存活块涨到 1,255 个，理论上该有 ~ 2 GiB 的差值，实测差值直接塌到 0 附近。

与此同时，还有一件更让人不安的事：哪怕完全不加 pad，驱动计数器也比 HIP 自己的 ledger 高出一块——逐次采样统计下来，这个差值最小值就是 2,213 MiB，中位数 2,445 MiB，整个训练过程从没低于 2.2 GiB；而带 pad 的跑，这个差值稳稳贴在 0 附近。也就是说：不加 pad 的时候，账上凭空多出来一块 2.2 ~ 2.4 GiB 的"幽灵占用"——驱动认，HIP 自己不认。

到这一步，孤立探针和真实训练给出的是两个互相矛盾的世界：孤立场景里，"每个块 × 2 MiB"这套账精确到小数点；训练场景里，这套账完全不成立，而且平白无故还多出一块没人认领的显存。这两组数字，一组约 2 GiB、一组约 2.2 ~ 2.4 GiB，量级又实在太接近，不像是巧合。

于是问题从"pad 花了多少钱"变成了一个更根本的问题：**这个进程身上到底有几本账，它们各自记的是什么，为什么会打架？** 下面几轮的测量，就是冲着这个问题去的。

### 8.1 先把"应该是什么样"算出来，再看现实怎么打脸

在真正挂上探测仪器之前，我们得先把让人头秃的"直觉"捋清楚，把它变成一个白纸黑字、可以被证伪的假说，不然后面的折腾全是在瞎忙活。

pad 一旦非零，每一笔请求都不再是 2 MiB granule 的整数倍了，runtime 只好为它多留一整颗 granule。在进程被冻结的那一瞬间，系统里正好有 1,213 个存活的内存块。好巧不巧，它们原本的大小正好卡在 granule 的边界上。只要稍微懂点底层逻辑就能算出来：

```
1,213 × 2 MiB = 2,426.0 MiB
```

这就是理论上"16 pad 应该比 0 pad 多占的显存"。它从请求量直接硬推出来，不依赖任何探测仪器；而这 2.4 GiB 既然是真的多占用了，理所应当每一本账都应该清晰地显示出它来。

而现实狠狠地打了一巴掌（两列干净数据来自第二轮，即纯 HIP 回放、没有 hook 也没有 torch；第一轮那个戴着 hook 的训练进程给出同样的跳变形状——11,895.3 → 12,210.9，差 +315.6——但它的 ledger 列撞在振荡相位上，做不了这个算术）：

| 仪器 | 0 pad | 16 pad | 差 | 相对"应该多 2,426 MiB" |
| --- | --- | --- | --- | --- |
| HIP ledger | 9,302.0 | 11,728.0 | **+2,426.0** | 分毫不差 |
| 驱动计数器 | 11,402.0 | 11,718.0 | **+316.0** | 只有预期的 **13%** |
| 进程地址空间（renderD128） | 11,334.0 | 11,650.0 | **+316.0** | 同上 |

到这里，离谱的事情出现了：我们发现 ledger 自己的账本和底层驱动的账本居然打起来了。账本信誓旦旦地说"确实多了 2.4 GiB"，驱动却两手一摊表示"我只看到多了 0.3 GiB"。中间凭空蒸发了一个远超测量误差的天文数字——这就是所谓的"两本账对不上"的第一形态。

接下来这一步是整幕的关键。我第一反应是"肯定是驱动计数器出 bug 了"——但这毕竟只是个直觉，不能拿来当证据。所以我得把它当成一个正经的假说，并且拉来另一个候选假说当对照组，用它们各自能推导出的预测数字来做个交叉审判：

| 读数 | 它在说什么 | 预言 0 pad 的计数器 | 预言 16 pad 的计数器 |
| --- | --- | --- | --- |
| A：驱动瞎了 | 驱动根本没看见"每个块多要的那一颗 granule"，它只看得到我确实申请的净土 | ≈ ledger 的 9,302（看不见任何额外的东西） | 也 ≈ 9,302（ledger 涨的那 2,426 它全漏掉） |
| B：账上本来就有幽灵 | 驱动是诚实的，只是 0 pad 时账上本来就挂着约 2.1 GiB——驱动看得见、而 ledger 死不承认的内存 | ≈ 9,302 + 2,100 = 11,402 | ≈ 11,402 + 2,426 - 2,110 = 11,718 |

实测结果一出：11,402.0 / 11,718.0。假说 B 完美命中（误差 0.4 MiB，这在计数器大约 15 MiB 的量子化误差面前根本不算什么）。而假说 A 在 0 pad 那一回合就已经偏到姥姥家去了，差了足足 2,100 MiB——如果驱动真的是瞎的，我应该在 0 pad 和 16 pad 的时候都看到紧贴着 9.3 GiB 的读数，可实际上它们全都在 11.4 GiB 以上。

也就是说，在不加 pad 的时候，账上本来就常年挂着约 2.1 GiB 没人申请的幽灵显存——驱动老老实实记了账，但我的分配一个都没指向它。而加了 pad 之后，这片幽灵显存莫名其妙地消失了。一进一出：+2,426 - 2,110 = +316，这正是为什么驱动从 0 pad 到 16 pad 看起来只动了 0.3 GiB。

当然，为了防止自己被某些低级的错觉骗了，我顺手把几个最容易捣乱的"嫌疑人"也给毙了：

"多出来的 2 GiB 是 hook 自己的开销？"绝对不是。pad 设成 0 的 hook 在行为上就是个纯观察者（padded == size，4949 行一条不差），而它自己的内存脚印是个死常数——把训练进程与纯回放逐档对齐，外部 ledger 的偏移是 530.00 MiB、renderD128 是 432.2 MiB、计数器是 492.57 ~ 492.88 MiB，四档逐字节相同。顺带完成了一个漂亮的核对：训练进程 0 pad 的计数器 11,895.3 减去这个常数等于 11,402.4，正是纯回放单独跑出来的那个 11,402.0。

"那是 torch 的运行时搞的鬼？"它其实就混在刚才说的那个常数里，而且同样完全不随 pad 变化。

"是不是驱动把页表当成显存算进去了？"纯属胡扯。哪怕加上所有的内核页表开销，在每个 pad 上也都只有 3.9 ~ 4.2 MiB，比那 2.1 GiB 足足小了三个数量级。

### 8.2 第一轮：四个 pad，冻在同一个位置

为了逮住它，我干脆给进程下了一剂猛药：在 step 5 快跑完的时候，我直接用 SIGSTOP 把 trainer 给强行冻住了（桩插在 trainer/loop.py，实验后已撤销、与 HEAD 一致）。我连续跑了四次，唯一改变的变量就是 AMDFQ_PAD_BYTES（0 / 16 / 64 B / 1 MiB）。四次实验，进程都死死停在同一个位置（state.json 的 training.step = 4、step 4 的 loss = 0.1005521 四次完全相同），并且处于冻结态不退出，这下两套口径的仪表都能在静止状态下放心读取了。

这四次的分配历史可以说是逐字节相同：hipMalloc 2,994 次、hipFree 1,775 次、活块 1,219 个 / 9,661,579,264 B；run id lllj_20260917_202744 / _203050 / _203412 / _204138；冻结时刻（CLOCK_MONOTONIC）47527.2 / 47713.1 / 47914.9 / 48360.9。

| 项（MiB） | 0 pad | 16 pad | 64 pad | 1 MiB pad |
| --- | --- | --- | --- | --- |
| hook 活表：活块 / 请求字节 | 1,219 / 9,214.0 | 1,219 / 9,214.0 | 1,219 / 9,214.0 | 1,219 / 9,214.0 |
| 回放：Σ round_up(size, 2 MiB) | 9,220.0 | 9,220.0 | 9,220.0 | 9,220.0 |
| 其中恰好是 granule 整数倍的块 | 1,213 | 1,213 | 1,213 | 1,213 |
| 回放：Σ(padded − size) | 0 | 0.02 | 0.07 | **1,219.0** |
| 进程自己的 ledger（冻结前最后一条样本） | 9,933.0 | 12,183.0 | 12,091.0 | 12,183.0 |
| 驱动计数器（冻结态，30 s 稳定） | **11,895.3** | **12,210.9** | **12,211.0** | **12,211.0** |
| 外部 ledger（冻结态，77 个样本全同） | **11,942.00** | **12,258.00** | **12,258.00** | **12,258.00** |
| renderD128 映射字节 | 11,766.2 | 12,082.2 | 12,082.2 | 12,082.2 |
| 相对 0 pad 的差（计数器 / 外部 ledger / renderD128） | — | +315.6 / +316.0 / +316.0 | +315.7 / +316.0 / +316.0 | **+315.7 / +316.0 / +316.0** |

（精确字节：外部 ledger 0 pad 是 12,522,094,592，三档非零 pad 全都是 12,853,444,608——逐字节相同，比 0 pad 刚好高出 331,350,016 B = 316.000 MiB。）

这时候，"向上取整到某个固定颗粒"这一大家子的解释，在这里遭到了团灭。我试着用这张表去反推那个神秘的"颗粒度"到底是多少：

| 假设取整颗粒 X | pad 16/64 的预期 | **pad 1 MiB 的预期** |
| --- | --- | --- |
| 4 KiB | 4.8 MiB | 1,219.0 MiB |
| 64 KiB | 76.2 MiB | 1,219.0 MiB |
| **256 KiB** | **304.8 MiB** | 1,219.0 MiB |
| 512 KiB | 609.5 MiB | 1,219.0 MiB |
| 1 MiB | 1,219.0 MiB | 1,219.0 MiB |
| 2 MiB | 2,426.0 MiB | 2,426.0 MiB |

你看，只有 256 KiB 那一档勉强能解释 16/64 字节 pad 搞出来的量级（304.8 预期对 315.6 实测，残差 3.6%）。但是，别高兴得太早：同一个模型如果套用在 1 MiB pad 上，至少得多花 1,219.0 MiB。请注意，这是个铁打的下界，不是什么拟合值：1,219 个活块每个都实打实地多要了 1 MiB，算下来 Σ(padded - size) = 1,278,214,144 B，任何按请求字节记账的口径都绝对躲不开这个数。结果呢？实测只多了可怜的 0.066 MiB。

于是真相的形状终于浮出水面了：只要 pad 不是零，立刻就会蹦出一个 +316.000 MiB 的台阶，然后直接饱和，哪怕你把 pad 往死里加大，它也纹丝不动。（其实还有一条神补刀的旁证：hook 日志尾部有三笔 caller=libc10_hip.so+0x41efa 的返回地址，它们之间的间距在 0 pad 时是 4 MiB，而在三档非零 pad 下全变成了 6 MiB——同样是"只要有 pad 就变，绝不随 pad 长大"。）

顺便提一句，这里有两个深坑，每一条都是后续读数必须要遵守的铁律：

运行中的两本账其实在疯狂劈叉：在冻结前 8 秒内，计数器像疯了一样在 7,595.4 ~ 13,055.3 MiB 之间反复横跳，同一时刻成对取样的差值更是能在 -1,042 到 +3,540 MiB 之间乱甩；但只要进程一停，两本账立刻老老实实地贴近到 47 MiB 以内。所以，表格里"冻结前的最后一条样本"（9,933.0 / 12,183.0 / …）绝对不能拿去和任何冻结态的数字直接比对——它不过是撞在振荡相位上的一个倒霉快照而已。

千万别手贱用 kill -CONT 污染日志：你想杀掉被 SIGSTOP 冻住的进程，就得先发 CONT 唤醒它，结果就在那一秒里，进程欢快地继续跑，日志尾部就神不知鬼不觉地混进了新记录（原始日志里有 3,285 次 hipMalloc，而真正的冻结态只有 2,994 次）。所以，截断文件必须老老实实用日志自带的时钟（第二列是进程内相对秒数），要是敢拿系统的 CLOCK_MONOTONIC 去过滤，你就会悄无声息地读完一份被污染的完整文件。

这一轮跑完，留下了三个悬案：(a) 计数器多出来的那部分，到底是真金白银的内存，还是记账系统搞出的乌龙？(b) 那个长得极其像"256 KiB"的台阶到底是个啥？(c) 为什么0pad和16pad、1MiB pad的区别都远远没达到应有的数量级？

### 8.3 第二轮：把 hook 和 torch 一起摘掉

第一轮实验里，咱们带着 hook 又压着 torch，嫌疑人太多了，根本分不清究竟是"pad 自己的贡献"还是"hook 和 torch 夹带的私货"。于是我决定把它们全踢出局，直接手搓了一个纯 HIP 程序。

这个程序什么花里胡哨的都不做，就是按冻结那份日志里的操作流，逐笔硬放：没有 LD_PRELOAD，没有 hook，没有 torch，只有纯粹的 hipMalloc / hipFree / hipHostMalloc，加上 hipMemGetInfo 和 sysfs 读取；跑完之后它会自己乖乖 SIGSTOP。四档实验只改了 --pad 参数（0 / 16 / 64 / 1 MiB），四次全跑的都是同一个二进制文件（sha256 8d3b2b0f8848aec6），也是从同一份起始基线起步。

纯 HIP 程序的四档出炉结果：

| 项 | pad 0 | pad 16 B | pad 64 B | pad 1 MiB |
| --- | --- | --- | --- | --- |
| `Σ(padded − size)` | 0 | 19,504 | 78,016 | 1,278,214,144 |
| 进程自己的 ledger used | **9,302.0** | **11,728.0** | **11,728.0** | **11,728.0** |
| 驱动计数器（冻结态） | **11,402.0** | **11,718.0** | **11,718.0** | **11,718.0** |
| 外部 ledger used | **11,412.0** | **11,728.0** | **11,728.0** | **11,728.0** |
| 计数器 − ledger | **+2,100.4** | **−9.66** | **−9.67** | **−9.66** |
| 恰好 2 MiB 的映射 | 1,925 | **1** | **1** | **1** |

（精确字节：进程自己的 ledger 在 pad 0 时是 9,753,853,952，而在三档非零 pad 下，全都是 12,297,699,328。）

这一轮跑完，最核心的结论其实就一条：剥离掉 torch，用纯 HIP 回放照样如此，这一切跟 torch 没半毛钱关系。

### 8.4 第三轮：写满哨兵，再一口气抢光

前两轮查了半天，其实查的都是"账"——无论是驱动的计数器，还是 HIP 自己的 ledger，说破天也只是某一层软件写在内存里的几行数字，而数字，是可以撒谎的。驱动计数器可能犯糊涂算错，ledger 也可能在藏匿私房钱没有如实申报。但有一件事绝对骗不了人：物理 GPU 凭空是变不出显存颗粒的。能实实在在申请出来、能写进数据、还能原封不动读回来的，才是真真正正的显存。所以这一轮我决定谁的账都不信了，直接去拷问内存本身。

我又写了一个极其干净的独立程序（同样把 hook 和 torch 踢了出去），专门重放 pad 0 的流。这次我不仅申请，我还要往每一个分配块里打满哨兵（用 seed(slot) + i × 0x9E3779B97F4A7C15 写进去，然后让内核负责重算期望值并统计不匹配的字数，同时用 atomicCAS 记下第一个敢不匹配的位置）。接着，我按 ledger 自己吹嘘的 free 额度，一刀不剪地精确申请、写满。最后，把仍然存活着的所有分配块，逐字回读，验明正身。

| 项 | `sent0`（一次性） | `sentA`（2 MiB 逐块 + 归还） | `sentB`（一次性 + 归还） |
| --- | --- | --- | --- |
| 回放结束时 ledger used / free | 9,452.0 / 6,852.0 | 9,452.0 / 6,852.0 | 9,452.0 / 6,852.0 |
| 申请 / 实得 | 6,852.0 / **6,848.0** | 6,852.0 / **6,842.0**（3,421 块，第 3,422 次失败） | 6,852.0 / **6,846.0** |
| 归还后 ledger | — | **9,452.0 / 6,852.0**（逐字节回到原值） | **9,452.0 / 6,852.0** |
| 归还后计数器 | — | 12,914.6（比抢光前**高** 1,368.0） | 9,434.5（比抢光前**低** 2,112.0） |
| 哨兵写入 / 回读校验字数 | 写入 5,750,915,072 | 回读 1,207,697,408 | 回读 1,207,697,408 |
| 不匹配 | **0** | **0** | **0** |
| GTT / `VmSwap` / 主机 SwapFree | 34.938 / 0 / 全程不变 | 同 | 同 |

两条极其震撼的结果：

一、ledger 对它自己的客户，是个诚实的好人。ROCr 敢说还剩 6,852.0 MiB，那就是真能交货，并且绝对没有去 GTT 里面拿系统内存糊弄人——我在测试项中死死钉住 GTT 纹丝不动，就是为了印证这一点。满场打满哨兵，零错率读回。等归还之后，账目逐字节乖乖回到 9,452.0 / 6,852.0。

二、但计数器彻底疯了，而且还走出了两条方向完全相反的野路子：一条比抢光前莫名其妙高了 1,368.0 MiB，另一条却诡异地低了 2,112.0 MiB。更离谱的是，这两个数，只要逐个映射去对，居然全都能对上——一条多出了 +684 个 2 MiB 映射（684 × 2 = 1,368 ✓），另一条少了 -1,056 个（1,056 × 2 = 2,112 ✓）。

我把十一个检查点全部摊在桌子上，那个潜藏的规律就像鬼影一样浮现了：

```
驱动计数器 - 自己的 ledger = 2 MiB × (恰好 2 MiB 的映射数 - 活着的 2 MiB 块数) - 21.4 MiB
```

十一个点里足足命中了十个，残差死死地钉在 -21.4 / -21.5 MiB 上（唯一的那个例外，是我唯一一次读数前忘了等落定的手贱操作）。也就是说，计数器高出来的那一大块，百分之百是由这些幽灵般的 2 MiB 映射给堆出来的；而 ledger 打死都不认这些账。只有当设备真的被填满时，它们才会灰飞烟灭（sentA 抢光之后，4,292 个映射里有 4,290 个是货真价实的存活 2 MiB 块，无主的幽灵只剩下可怜的 2 个）——这也是为什么"把显存抢光，反而能超出计数器表面可用量"的奇葩原因。

### 8.5 第四轮：请一个进程里没有 ROCr 的第三方来裁决

第三轮结束的时候，我面对的是一个怎么解释都说得通的罗生门：

A（HIP/ROCr 进程）大声疾呼还剩 6,852.0 MiB，而且只要它自己去要，就真能一分不少地拿到手——写满哨兵、回读零报错；

那么真相要么是 ① 驱动的计数器虚报了（那块地方在硬件上本来就是空着的，全是驱动自己算多了），要么是 ② ROCr 在疯狂私吞（它早早向驱动多圈了约 2 GB 当"战备储蓄"，但这笔账没记在用户头上；等用户真急需时，它再悄悄吐出来——由于整个过程对驱动完全透明，所以 A 自己去要，当然觉得一切正常）。

破局的唯一办法，是去请一个一辈子没见过 ROCr 的外人 B，让它去要那 6,852.0 MiB 试试水：被 ROCr 私吞的内存，对外人 B 绝对不可用；而如果只是驱动虚报，那这块地对 B 就是敞开的。判决的标尺，我在动手测量之前就提前钉死在黑板上了（B 自身那点开销在两次相减里直接被抵消了）：

| 假设 | 预言 `M_idle − M_withA` |
| --- | --- |
| ① 计数器虚报，ledger 是个老实人 | 9.151 GiB |
| ② 计数器老实，全是 ROCr 在私吞 | 11.235 GiB |

两个预言之间差了足足 2.08 GiB，完全是一次二值可判的死斗。

我请出了 Vulkan (RADV) 来当这个铁面判官。因为它直接走 libdrm 和 amdgpu ioctl，跟 ROCr 八竿子打不着，完全是一个独立的第三方，也不需要什么着色器编译器就能直接强拔显存。为了自证清白，B 把自己的 /proc/<pid>/maps 亮了出来：B 的进程里只有 libvulkan_radeon.so 和 libdrm_amdgpu，绝对没有半个 libhsa-runtime64、libamdhip64、libamdocl64 的影子。

为了验证这一点，我设了个局，让判官 B 分三个阶段下场，每走完一段就老实 SIGSTOP 冻住自己：P0 阶段只建 instance/device（必须趁设备还空着时抢先建好，顺手量出自己的脚印）；P1 阶段先拿着"定值探针"照着 A 报出的 ledger_free 精确索要，如果被拒，就开启降维打击（1 GiB → 256 → 64 → 16 → 4 → 2 → 1 MiB）反复敲门直到被彻底拒绝，每拿到一块立刻写满哨兵；P2 阶段全量暴力回读。每一块拿到的内存算不算数，全靠正面铁证：只有计数器增量约等于申请量（误差 ± 256 KiB），并且 GTT 纹丝不动，才算是在显存上；否则立马释放退货，降档重来。两侧的哨兵常数被我设得完全不一样（A 拿着 0x9E3779B97F4A7C15，B 拿着 0xD1B54A32D192ED03），只要敢发生越界乱写，光看数据里的常数就能抓出作案真凶。

一共跑了三次：base3 = B 独角戏；r0 = A 独角戏（同 session 留作参照）；dec0 = 决定命运的一战——B 停在 P0 待命 → A 走回放然后冻结 → 30 秒完全无干扰的死亡凝视（保持观测）→ B 冲上去狂抢 → A 苏醒后再跟着抢 → 双方对簿公堂，全量回读。

| 检查点 | A 的 ledger used / free | 驱动 vis | 驱动 gtt | B 实得 |
| --- | --- | --- | --- | --- |
| `base3` B 单独 | — | 17,086,889,984 | 283,975,680 | **17,011,048,448 B（15.843 GiB）** |
| `r0` A 回放后 | 9,911,140,352 / **7,184,842,752** | 12,107,448,320 | 21,889,024 | — |
| `r0` A 抢完 | 17,095,983,104 / 0 | 17,077,714,944 | 21,889,024（**没动**） | — |
| `dec0` a1（A 冻结） | 9,911,140,352 / **7,184,842,752** | **12,138,266,624** | 290,328,576 | — |
| `dec0` a1 + 30 s | 同 | 12,138,307,584 → **12,138,266,624** | → 290,328,576 | — |
| `dec0` b1（B 抢完） | 同（**没变**） | **17,087,578,112** | 290,328,576 | **4,949,278,720 B（4.609 GiB）** |
| `dec0` a2（A 再抢） | 17,095,983,104 / 0 | 17,086,160,896 | **5,231,304,704** | — |

（在 dec0 这场战役里，B 的降阶梯之路相当憋屈：1 GiB 居然第一次敲门就被拒了 → 256 MiB × 2 → 64 × 1 → 16 × 2 → 4 MiB × 2 → 2 MiB × 1 → 1 MiB × 6，一共磨到了 18 块碎银，合计 4,609.0 MiB，这些全都通过了正面铁证的检验；另外还有 7 次因为被判"偷偷落进了主机内存"而当场释放退货。）

判决结果极其利落：

| | 值 |
| --- | --- |
| M_idle（B 独享能拿到） | 17,011,048,448 B = 15.843 GiB |
| M_withA（A 冻着时 B 实得） | 4,949,278,720 B = 4.609 GiB |
| `M_idle − M_withA` | **12,061,769,728 B = 11.235 GiB** |
| 假设 ① 预言（驱动虚报） | 9,825,157,120 B = 9.151 GiB → 差 2.083 GiB（错得离谱） |
| 假设 ② 预言（ROCr 私吞） | 12,062,609,408 B = 11.235 GiB → 仅仅差了 839,680 B = 0.007%（精准命中） |

终审判决：驱动计数器是个大老实人，是 ROCr 真的在手里死死攥着大约 2.07 GiB 的驱动级显存，并且它自己的 ledger 还厚着脸皮死活不认账。翻译成人话就是：HIP 拍着胸脯说库房还剩 6,852.0 MiB，外人真去提货却只能拿走 4,720.0 MiB，中间凭空消失的 2,132.0 MiB 全是 ROCr 自己偷偷攒下的私房钱。（第三方洗劫一空后，计数器停在 17,087,578,112 / 17,095,983,104——硬生生只给卡剩下可怜的 8.0 MiB。）

顺带还扯出了三条附加结论，随便单拎一条出来都够喝一壶的：

那 2.07 GiB 绝对是稳定的小金库，根本不是什么记账迟滞。在那 30 秒的死亡凝视里，计数器才微微动了可怜的 40,960 B，GTT 也只挪了 45,056 B。

ROCr 极其护犊子，这笔储备能且只能吐给它自己的客户。回看 r0 记录，A 居然能一口气吞下全部的 7,184,842,752 B，然而计数器只心虚地涨了 4,970,266,624 B、GTT 稳如泰山——这差出来的 2,112.0 MiB，就是 ROCr 从自己的私库里掏出来补给 A 的。所以，"ledger 的 free 额度是真的"这句话，对 ROCr 的亲生客户是句大实话，对外人就是句大忽悠。

显存真的被榨干的时候，ROCr 居然会拿主机内存顶包，而且一个字都不跟你说。在 dec0 里，外人 B 刚把 4.95 GiB 薅走，A 苏醒后居然还是眼都不眨地一口气拿到了全部的 7,184,842,752 B——更离谱的是，驱动计数器连动都不动（反而跌了 -1,417,216 B），而那边的 GTT 直接暴走，从 290,328,576 狂飙到 5,231,304,704（暴涨了 +4.94 GiB）！这批顶包的货回读毫无压力、零报错，而 hipMemGetInfo 呢？全程脸不红心不跳地把它们全算成是显存。没有任何报错提醒，这仅仅是一段无声无息、瞒天过海的狸猫换太子。

（另外补刀两个交叉验证：那个裸 C 写的 HIP 读数器，这次坚决站到了计数器这一边——在冻结态它坦白 used 11.293 GiB / free 4.629 GiB，跟第三方外人实际拿到的量差距不到 21 MiB；而且当 B 抢走 4.95 GiB 之后，它的数字连跳都没跳一下，这证明 HIP 的 free 雷达根本扫不到别的 API 分配的地盘。另外，两边哨兵的常数不一样，而双方各自回读自己的内存却全是零错误，这铁证如山地说明 A 的 7.18 GB 和 B 的 4.95 GB 压根就不是同一批物理页。绝对没有别名重叠。）

### 8.6 第八幕的答案

折腾了一大圈，把这三本账全部凑到一张桌子上对质（基于同一份冻结的活表：1,219 块 / 9,214.0 MiB），谜底其实也就解开了：

| 仪器 | 0 pad | 加 pad | 差 |
| --- | --- | --- | --- |
| HIP ledger（它的亲儿子还能要到多少） | 9,302.0 used / 7,002.0 free | 11,728.0 used / 4,576.0 free | +2,426.0 / −2,426.0 MiB |
| 驱动计数器（真金白银显存，第四轮作保） | 11,402.0 | 11,718.0 | +316.0 MiB |

真相大白，它们根本就不矛盾。因为这所谓的 pad 和"池子"，根本就是同一笔 granule 级别开销被变着法儿花出去的两种模式：

当你不加 pad 的时候，活块自己很乖，不占额外的 granule，但 ROCr 在背后悄悄留下了一整池大约 2.1 GiB 的真实物理显存拿来当私房池子——在驱动那边，这笔账已经被算成"已使用"了，但只要 ROCr 愿意，它可以随时掏出来赏给自己的客户。于是，这个进程当时真正还能调用的地盘是：4,902 MiB 的设备空闲，加上 2,114 MiB 的池子，正好 ≈ 7,016 MiB。这数字跟它自己 ledger 广告里吹的 7,002.0 MiB 严丝合缝。

但当你一加 pad 的时候，那大约 1,213 个乖乖对齐的活块，每个都被硬塞进了一颗终身甩不掉的额外 granule（直接报销 +2,426 MiB）。这么一折腾，私房池子瞬间破产消失。于是它能用的钱，就只剩下那些清汤寡水的设备空闲了：16,304 - 11,718 = 4,586 MiB，这同样死死咬住了 ledger 里显示的 4,576.0 MiB。

而在物理设备的维度上，设备层面的净差值 = 2,426 - 2,110 = 316 MiB，这恰恰就是驱动计数器上面跳动的那 316 块碎银！

所以，对于 ROCr 自己的亲生客户（也就是咱们的 trainer）来说，加上 pad 的代价，那就是实打实地烧掉了整整 2,426.0 MiB（也就是 2.37 GiB）的可用救命钱，而绝对不是计数器上轻描淡写的区区 316 MiB。在第七幕里算出的那个 +2,534 MiB，其实就是完全相同的原理在 run 跑到巅峰时刻（1,255 个活块，恰逢保存 checkpoint 那要命的一瞬）的测量写照。

两句必须得刻在脑子里的教训：

hipMemGetInfo 这玩意儿，千万别拿它去判"这卡还剩多少余粮"。这家伙对自己人乐观得没边，一口气虚高约 2.1 GiB（这破池子既挂在驱动的名下吃空饷，它又敢夸口能再交出来）；但要是对外人，它又往死里藏着掖着（第四轮铁证：外人累死累活只能讨出 4,720.0 MiB，而它 ledger 广告上可是赫然写着 6,852.0 MiB 呢）。

显存真的被榨干的时候，系统是绝对不会大发慈悲给你报错的，它只会偷偷摸摸地塞给你一堆主机内存。（第四轮 dec0 那一战：显卡明明已经被塞爆了，hipMalloc 照样装作风平浪静地返回成功，而那些装不下的数据差量，全都被静默发配进了 GTT 里去喝西北风。）

### 8.7 附带收获：我是怎么骗到自己的

这一幕的价值有一半在这里。以下几个坑，每一个都曾经让我的读数错得理直气壮，现在都写在 `amdfq.md` §11.7 里：

| 坑 | 它骗了我什么 | 现在的规矩 |
| --- | --- | --- |
| 计数器在分配突发期间瞬时虚高 | 某次在冻结瞬间读到 14,673.1 MiB，0.25 s 后是 11,605.1 MiB，之后还有 58.6 MiB 的慢衰减 | 每次读数前 `--settle 500`（同步 + 睡半秒）；任何"冻结瞬间"的读数都要等它落定 |
| 外部读数器自带脚印 | 第一版用 torch 写，它自己占 2,132.0 MiB，全落进它的 `used` 里 | 换成裸 C 读数器，单独量它的底噪（82.0 MiB）；外部列不能和进程内列直接比 |
| `kill -CONT` 污染日志 | 杀掉 `SIGSTOP` 进程得先 `CONT`，那一秒的日志被算进了冻结态 | 截断必须用日志自己的时钟（进程内相对秒数） |
| 每次跑必须空卡起步 | 一次残留进程占 164 MiB，把某个检查点抬高；另一次残留 9.4 GiB，让下一跑在**第 267 个分配**上 OOM 退出 | 起跑前确认回到空闲基线；收尾必须 `CONT` → `KILL` → 复查基线 |
| 落点必须逐块正面证明 | 4 MiB 的块落进主机内存，从一个 8 MiB 的阈值下面溜过去了 | 判据改成"计数器增量 ≈ 块大小 且 GTT 不动"，与块大小无关 |
| RADV 会静默回退 | 显存申请失败时它把块塞进主机内存，日志里看不出区别 | **必须 `RADV_DEBUG=nogttspill`**；`VK_EXT_memory_budget` 的堆用量**不能**用来判落点（它把主机内存的块也记在"被申请的那个堆"上） |

（第 4 条对应的那次事故把整机拖进过 OOM。事故本身不必写，但它留下了这套字节上限与看门狗，所以规矩留着。）

## 第九幕 · 路线一：自己写一个分配器

> 证据：[`../amdfq.md`](../../amdfq.md) §12

第七幕算完账，得出的结论很直接："这套多要内存的机制是成立的，但这粗暴的设计价格实在太坑"。当时我脑子里蹦出来的第一个念头，就是干脆把 pad 的核心逻辑直接夺权，自己接管。

我是这么盘算的：既然 pad 之所以贵得出奇，是因为 runtime 给每一个小块都傻乎乎地单独多买一颗 granule，那我就甩开它，直接调底层的 VMM API（hipMemAddressReserve/hipMemCreate/hipMemMap/hipMemSetAccess），自己去圈一大片地址空间，自己操刀切块。最骚的是，我在每一块的屁股后面，全给它们映射上同一个共享的 pad granule——这么一来，整个进程用来防越界的 slack 预算，从原本的 1,255 颗 granule，瞬间暴降到只需要买单 1 颗 granule。

从结果来看，它确实做到了两件事：一是把那高昂的成本给彻底打下来了（全服共享 1 颗 granule），二是它也真真切切地把那个要命的 step-10 fault 给抹平了。

然后，你猜怎么着？它搞出了五花八门的死法，用五种完全不重样的方式把进程给玩坏了。

出问题的压根就不是那个 fault，而是周围的邻居遭了殃：两个毫无关联的 kernel 突然抽风开始抛出非法的 shader 指令，某个 wave 的 PC 像喝醉了一样直接飞到了未映射的野地址上，到处是野指针在狂舞，甚至某一步的 loss 毫无预兆地变成了 NaN。足足五种死法，至今没有一种能给个痛快的科学解释。

当然，这趟浑水没白蹚，我至少排除了两半的错误答案（老实说，排除错误这步比失败本身更有价值）：

真不是 VMM 调用本身在放毒。我不死心搞了个 shadow 模式（AMDFQ_VMM_SHADOW=512）：我把每一笔真实的分配动作，原封不动地镜像到另一片无人读写的 VMM 内存上，让它把 hipMemAddressReserve/hipMemMap/hipMemSetAccess 的全套序列都老老实实走一遍，唯一的区别是不去给任何操作数服务。结果进程健康得一批。顺带一提，那个 shadow 里的每一页，背后也全是映射着同一个共享对象——这也算歪打正着，给后来的路线二埋下了一步好棋。

这锅也不该"切地址空间的方式"来背。我一怒之下换成了 per-allocation 布局（每一笔分配都自己独立 reserve、自己独立 free，连 arena 和 free list 都懒得搭了），结果该崩还是崩。

而且，对照组活蹦乱跳的。同一份一模一样的配置，我加上 AMDFQ_VMM=0（也就是这套机制什么活都不接）再跑了一次，人家直接丝滑地杀到了 step 66，损失数值 0.0862 / 0.0528 / 0.1023 / 0.0067 / 0.1074 稳得一批——这一路上连个异常的影子都没见着。

所以，最后的定案结论是："VMM 调用有毒"这个冤假错案被平反；真正要命的毒点，是"把操作数本身给建在 VMM 内存上"这波骚操作。只要是由我自己的分配器亲手递出去、且被 kernel 当作操作数来啃的内存，就会不知什么原因，像病毒一样疯狂撕裂进程的其他状态——这实在是一个至今仍悬而未决的灵异现象，但从它发作的症状来看，它更像是一出"进程自身状态遭遇了随机降维打击"的惨剧，而不单单是"kernel 写得烂"那么简单。

路线一到此封存。（不过它的研究价值我没打算扔：毕竟，一个随便写写就能让两个不相关的 kernel 狂抛非法指令、能把 GPU 忽悠去野指针、还能把 loss 搞成 NaN 的诡异分配器，这背后绝对藏着一个大瓜没啃出来。）

## 第十幕 · 路线二：只给尾部站一个岗

> 证据：../amdfq.md §13，以及最终的控制组实测，代码在 ../amdfq/amdfq_tail.c

既然路线一死在"全盘接管分配器"上，那路线二我就只能苟一点：我不去动核心逻辑，就让 hipMalloc 继续干它的分发活儿，我只负责在它分配完之后，悄悄在尾部补一刀站个岗。

这套路统共分四步，非常干脆：

hipMalloc 完事返回后，我直接去捞这块内存的 extent 范围（老老实实用 runtime 自家的 hipMemGetAddressRange 查，查完再按 granule 往上取个整）。

然后我抛出一个灵魂拷问：紧贴在 extent 后面的那 16 个字节所在的这页纸，究竟有没有被什么东西给映射着？如果 hipMemGetAddressRange 说它其实正好落在了隔壁另一个还活蹦乱跳的分配块里，那就没事了——就算 kernel 越界读，读出来的也是合法地带，根本不可能把进程搞崩。于是拍拍屁股，什么都不用做。

如果那地方正好是真空（也就是不填就会直接 fault 暴毙的那种情况），我就果断用 hipMemAddressReserve 把那一页给圈下来——这里的 hint 必须一分不差地砸在那里，歪了一点都不算数——接着把一个共享对象直接映射进去（hipMemMap + hipMemSetAccess 走起）。这个共享对象在进程启动时用 hipMemCreate 搞一次就够了。

等到 hipFree 毁尸灭迹的时候，先利索地把这块自家的守卫给卸掉。卸完之后再回马枪问一遍：刚才被干掉的这一块，它活着的时候是不是在给前面的那块当肉盾（前一块的守卫）？如果是，且前一块现在还活得好好的，那不好意思，前一块马上就需要一页全新的守卫来替补了。

为什么死活非得是"同一个"共享对象？这可不是我有什么系统级的整洁癖，而是迫于无奈的设计铁律：runtime 这帮大爷，会丧心病狂地把你的每一次 hipMemCreate 对象，全都按 2 MiB 显存的规格给你记上账，哪怕你这个对象骨子里其实只有 4 KiB 大小。如果真的是一块地配一个专属对象，那 hipMemGetInfo 里的数据就会跟着每块暴涨 2 MiB，咱们前面千辛万苦想省下来的钱，就全给白白烧回去了。

万一 hint 死活落不到目标页上怎么办？（实测概率大约 0.2%，那点地方实际上就是被 runtime 自己圈去预留了）这题简单粗暴：我直接把这块地原样退回去，然后老老实实按 size + 16 重新申请一遍——没错，就是直接退回第七幕的那套 pad 方案，把它当成这条险路最后一道托底的保险丝。

### 10.1 真相大白：它到底替我们抢回了多少显存

说实话，我差点就把路线二当成工业垃圾给扔了。

在早期测试的时候，我干了一件极蠢的事：我死死盯着驱动计数器去评估收益。结果发现，挂上尾部守卫后，驱动计数器居然比 pad-16 时还高了大约 391 MiB！如果不是第八幕我死磕到底，把 ROCr 那个 2.1 GiB 幽灵私房钱的账本给彻底扒了个底朝天，我当时可能直接就把这套代码删了。

为了彻底把账算明白，我拉齐了三个组（不挂补丁、pad-16、尾部守卫），用同一个 seed、同一段真实的分配流，跑到同一个冻结点上（第 5 步，1,219 个活块）。这次我不看别人，我只看进程内 ledger——也就是 ROCr 拍着胸脯保证"这个进程还能要到多少真金白银的可用显存"：

| 组别 | 进程还能要到的可用显存（free） | 驱动计数器（vis） | 结局 |
| --- | --- | --- | --- |
| 不挂补丁 | 6,369.0 MiB | 11,895.2 MiB | 第 10 步当场暴毙 |
| pad-16 兜底 | 4,561.0 MiB | 12,210.9 MiB | 活下来了 |
| 尾部守卫（路线二） | 6,467.0 MiB | 11,916.1 MiB | 活下来了 |

看到第一列的落差了吗？这就是第七幕里那个让我肉痛的代价的真实面目。

pad-16 的代价，绝对不是驱动计数器上轻描淡写涨出来的那区区 316 MiB。因为强制破坏了 granule 对齐，它硬生生把 ROCr 那一池子原本能随时拿出来救命的幽灵显存给毁了。落实到进程头上，pad-16 实际上暴力剥夺了整整 1,808.0 MiB（将近 1.8 GiB！）的真实可用显存。等跑到第 100 步的巅峰期（1,253 个活块）时，这个可用显存的差额更是直接飙到了 2,484.0 MiB。

而尾部守卫，把这笔巨款一分不少地全给抢回来了。

在第 5 步时，尾部守卫让进程拥有 6,467.0 MiB 的自由资金，不仅扛住了越界读，可用量甚至和"不挂补丁"时完全在同一个水位线上。那么，路线二为此付出的真实物理代价究竟是多少呢？我查了底层实给的字节数：仅仅多了 7.0 MiB。这 7.0 MiB 里，包含了一颗 2 MiB 的共享对象，加上 7 个因为跑偏而无奈走了 pad 兜底的活块。

也就是说，路线二用区区 7 MiB 的成本，完美换回了 pad-16 烧掉的约 2.4 GiB 显存。

### 10.2 性能代价：几乎隐形的守卫

把防线从前端（pad）移到后端（拦截后映射），操作变复杂了，它会不会拖慢训练？

我先用纯 HIP 探针在热池里做了一波压力测试。账面上的数字确实不好看：因为每做一次分配都要连带查状态、切映射，hipMalloc 和 hipFree 的耗时合计从原本的 34.1 µs 飙升到了 58.4 µs（单次操作多了约 24 µs 的 CPU 开销）。按每步训练大约 372 次分配来算，CPU 侧大概会多花 9 ms。

但在实际的训练场里，这些理论开销就像撒进海里的盐。由于 GPU 的重度计算完美掩盖了 CPU 侧的记账延迟，真实的逐步墙钟（wall_time）跑出来是这样的：

| 组别 | 步墙钟中位数（秒/步） | 相对基准慢了多少 |
| --- | --- | --- |
| 不挂补丁 | 1.1450 s | 基准（可惜活不过 10 步） |
| pad-16 | 1.1355 s | (因死得早，覆盖区间不同，难以直接对比) |
| 尾部守卫（路线二） | 1.1493 s | 仅仅慢了 0.3% |

哪怕在最保守的评估下，这条路线对整体训练时间的拖累也死死压在了 0.2% 到 1.0% 之间。

顺带一提，路线二的成功，也间接给第九幕的悬案盖棺定论了：之前路线一疯狂暴毙，绝对不是因为 VMM 调用本身有毒，也不是大规模共享映射有坑（路线二 99.8% 的分配都挂着同一个共享页，活得比谁都好）。真正把路线一搞走火入魔的，就是偏要把操作数本身建在 VMM 内存上这波迷之操作。

### 10.3 结案：它现在是默认行为

amdfq/amdfq_tail.c 里现在死死钉着上述的那四步铁律，并且它被设成了默认开启。第七幕那昂贵的 pad 彻底退居二线，只负责承接那可怜的 0.2% 映射失败的兜底活儿。

如果你哪天起了疑心，跑去加个环境变量 AMDFQ_TAIL=0 关掉守卫，让它退化回纯转发模式，那你就能在一分钟之内，原汁原味地重温最初那个把人折磨疯的 step-10 fault。换句话说，我现在甚至把这个该死的 bug 的复现开关，做成了我自己补丁里的一个小小环境变量。

（顺便提一下，仓库里的 start_train.sh 不会自动 preload 把它加载进来；想要用，必须显式地把 LD_PRELOAD 带上。这是我刻意立的规矩：像这种会从底层彻底扭曲内存布局的核弹级组件，绝对不该在没人知情的情况下，静默地在后台发飙。）

## 尾声 · 还没关掉的账

技术排错没有完美的童话结局，一份诚实的记录必须把那些烂尾的部分也亮出来。

一、到底有多少 kernel 会这么肆无忌惮地读超，老实说我不知道。影响面大概是 1,830 个可以发射的 bf16 kernel × 10 个形状 = 18,300 个作业，这份排查清单其实我已经生成好了存着（fixes/hip1/resources/bf16-overrun-jobs.tsv），但全量扫描我始终没有狠下心去跑（这在计划列表里叫 M4，至今挂在那）。原因很简单：我把成本给估错了。大头根本就不在发射测试本身，而是在于每一次触发 fault 被干掉之后，ROCr 得花足足约 7 秒钟去磨磨唧唧地复位设备——你要是按 fix3 的那个死亡率去推，真把这清单扫一遍，整整几个小时就全耗在重启设备上了。所以现在我唯一敢保证的是"这些 kernel 里面肯定有这帮喜欢越界读的惯犯"，至于"究竟有多少比例"，这我还真给不出数。同理，前面所有信誓旦旦证明"这些越界读是惰性的"证据，全都是基于那些在实战中真正被执行过的 kernel，绝对不代表这全部的 1,830 个都是良民。

二、fault 的响应机制本身会离奇失效——而且它会以一种让你的实验悄无声息变成废纸的方式搞你。2026-09-16 那天，大概从 16:45 到 17:58 的某一刻开始，每一次访问未映射显存，竟然再也不引发任何页错误去干掉进程了：系统里只剩下 GPU 保持 100% 满载空转、进程在 hipStreamSynchronize 里彻底迷失疯狂自旋（State: R、wchan: 0、voluntary_ctxt_switches 死死卡在 3，纯粹是用户态在轮询而根本没有阻塞），而内核日志里比脸还干净，一行都没有。无论是四个互不干扰的独立程序，还是两条完全不同的路径杀进 hipBLASLt，全都是这副鬼样子；而那些原本就不会触碰未映射页的安全形状，crc 却依旧稳如泰山。这症状只能靠重启才能解决——但诡异的是，那次重启又好死不死地顺带把内核从 7.2.4-zen2-1 升到了 7.2.6-zen2-1，所以"是不是状态卡死了被清空"和"驱动偷偷换了个 build"，这两件事死活分不开了。（那一次发病的实锤证据现在彻底没了：发病时我没反应过来挂探针，一重启，现场就被毁得干干净净。）

为什么这破事对我来说这么要命：因为我对所有缓解措施的评判，全都是死死钉在"只要 fault 发生，就一定会被系统爆出来"这个前提上的。一旦机器陷入了这种卡死失明的状态，"这次没崩"看起来就会像极了"这次根本没越界"。所以现在哪怕长跑之前，我都得先打一发 canary（探路鸟，fixes/hip1/repro_standalone.sh）：只要它崩了，就说明报警通路没瞎；如果它卡住了，那赶紧停手，说明机器又犯病了——这时候按 gfx1201-fault-response-wedge.md §4.2 里的抓鬼判定表，拿探针去挨个逼问是哪层出了问题：如果 gmc 计数为 0 → 那是 GPU 或底层固件直接罢工不上报；如果 gmc 有数但 KFD 的 evict/restore 卡死 → 恭喜，KFD 的状态机崩了；要是两者都正常而进程却装聋作哑 → 通知路径断了。

三、至于那约 2.1 GiB 的池子到底是留着干嘛用的，抱歉，我到现在也没查清。我知道 ROCr 会把它贴心地留给自家客户续命，我也知道外人费尽心机也偷不走一字节——但我就是不知道 ROCr 凭什么非要圈这么一块地、这块地留多留少的底牌策略究竟是个啥。你要知道，在一张 16 GB 的卡上，那可是一块外人借不到、ROCr 自己又烂在手里用不完的奢侈余量啊。

四、还有几笔死活对不平的烂账。那些一次性抢光内存的实验里，哪怕起点精确到逐字节相同，边界也还是会出现 ± 2 MiB 的迷之抖动；逐块释放之后，池子里竟然诡异地剩下了 684 个映射，而一次性全释放之后，则是暴跌 -1,056（池子像被彻底洗劫一空，并且再也没被重建过）——这中间严重的不对称，我也还没去跑代码验证。

最后一句。我最终交付的这个东西，其实根本算不上是一个"我把一切都修好了"的完美英雄故事。我既没能让 AMD 的底层 kernel 变老实，也没本事让 ROCm 那个倔强的内存管理学会懂事；我真正做到的，仅仅是在这两尊大神之间，硬生生地塞进了一块垫脚石，让那次不可避免的越界读，能有个软着陆的地方。代价嘛，就是让每个进程多吞一颗 granule；收益呢，是大手一挥找回了足足大约 2 GiB 的真实显存，以及，换来了一场能安安稳稳跑到 step 150 不暴毙的珍贵训练。

如果哪天，AMD 从架构底层良心发现，给出了那个"尾部必定有合法余量"的官方承诺，那我写的这个破补丁就可以毫不留情地删掉了——而我，会是一百个乐意亲手删掉它。

## 附录 A · 复现与使用

# 冒烟测试：随便跑一次 torch.zeros，看看这 hook 到底上没上膛
bash amdfq/hook.sh

# 真刀真枪训练（start_train.sh 本身可是不会自动 preload 的，要用就显式带上）
bash amdfq/hook.sh bash start_train.sh
# 这个跟下面是等价的：
LD_PRELOAD=$PWD/amdfq/cmake-build-debug/libamdfq.so bash start_train.sh

# 想复现最初那个折磨人的 step-10 fault？关掉尾部守卫，让补丁退化回纯转发模式

## 附录 C · 术语

| 词 | 意思 |
| --- | --- |
| **gfx1201** | AMD RDNA4 的 GPU 架构代号；本文这台 RX 9070 XT（16 GB）就是它 |
| **Tensile** | AMD 用来生成 GEMM kernel 的代码生成器；它生成的 kernel 名字长达 855 字符，编码了所有调优参数 |
| **bf16** | 16 位浮点（1 符号 + 8 指数 + 7 尾数），本文的训练精度 |
| DepthU | Tensile 在 K 方向展开的深度；K (mod DepthU) ≠ 0 就会走尾块（tail loop） |
| **macro tile / `MT64x128`** | 一个 workgroup 负责的输出块大小；自由维度不是它的整数倍就会出现边缘块 |
| **`Ailk` / `Bjlk`** | 操作数的内存布局（哪一维连续）；hipBLASLt 按布局 + 转置挑库文件 |
| **GLTr** | Global Load Transposed，AMD 那条 16 字节的转置 load 路径 |
| **DTV** | DirectToVgpr，把数据直接读进 VGPR 的解法变体；是那 157 个被规则拒掉的解法 |
| **guard page** | 紧跟在分配后面、故意不映射的一页；越界读撞上它就触发页错误 |
| **granule** | runtime 分配的最小颗粒，这台机器上是 **2 MiB**；请求会被向上取整到它 |
| **BO** | Buffer Object，驱动层面的一块显存对象 |
| **ledger** | `hipMemGetInfo` 报的用量账；本文里它和驱动计数器不是一回事 |
| **VMM API** | `hipMemAddressReserve`/`hipMemCreate`/`hipMemMap`/`hipMemSetAccess` 这一套：地址、物理对象、映射三者分开操作 |
| **M4** | 计划里"扫全部 1,830 个 kernel"那一步，至今未跑 |
