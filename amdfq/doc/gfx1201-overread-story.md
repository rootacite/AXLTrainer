# 一块多出来的内存

**gfx1201 的 bf16 越界读，和一场持续数月的追查**

---

**这是什么。** 一篇叙事。它讲一块 AMD RX 9070 XT（gfx1201）上的显存里发生过的事，以及我为了弄清它而走过的路：从"是不是桶形状没对齐"，到"这是 ROCm 出厂预编译 kernel 在读它不该读的地方"，到"改源码这条路走不通"，到"那就不修 kernel，给它一块合法的尾巴"，最后到"等等，为什么同一个进程有三本账，而且它们差 2 GiB"。

**这不是什么。** 它不是权威记录。权威记录是这几份，本文的每个数字，我都标了它出自哪一份的哪一节：

| [`live-data.md`](live-data.md) | 四轮测量过程的中文原始记录 |

**一句话结论。** gfx1201 上，hipBLASLt 派发的 bf16 Tensile kernel 会读出 A/B 操作数的末尾；幅度不超过 4 KiB，读到的值不进入结果，操作数末尾后面是已映射内存时完全无声——但只要那里是一页没映射的显存，GPU 就报页错误，进程当场被杀（`-6`）。既然这个读**从 kernel 一侧修不掉**，我就换了个方向：不去修那次读，而是让它落在一块存在的内存上。

## 第一幕 · 桶、对齐，和一个没人复核的结论

> 时间：几个月前。证据：[`../fixes/fix1.txt`](../../fixes/fix1.txt)

最初的症状很朴素：训练跑着跑着，进程就会毫无预兆地硬崩一次。

```
IOT instruction (core dumped)
amdgpu 0000:03:00.0: [gfxhub] page fault (src_id:0 ring:24 vmid:8 pasid:144)
GCVM_L2_PROTECTION_FAULT_STATUS:0x00801031
Faulty UTCL2 client ID: TCP (0x8)
RW: 0x0
```

当时的推理链是这样的，而且**每一步听起来都很合理**：

1. **VAE 陷阱。** 图像被 VAE 压缩 8 倍（`f8`）。当 `bucket_step = 64` 时，某些尺寸的桶会得到"是 8 的倍数、但不是 16 的倍数"的 latent——例如桶 `832×448` 给出 latent `104×56`。
2. **ROCm 更严格。** 与 CUDA 生态不同，AMD 的 ROCm（尤其 MIOpen 与 Flash-Attention 的 kernel）对非 16 字节对齐的维度**极不宽容**。
3. **越界访问。** 于是 GPU 的 wavefront 对着这些没对齐的 latent 矩阵做向量化 load 时"指针偏移算错"，越界读。
4. **`shuffle=True` 解释了"随机"。** 因为 `shuffle=True`，每个 epoch 的批次顺序都会变；如果连续几个"有毒"的桶被喂进同一个高度碎片化的分配器，就立刻炸。

对策看起来顺理成章：我把 `bucket_reso_steps` 从 **64 改成了 128**。这样 `128 ÷ 8 = 16`，latent 维度永远能被 16 和 32 整除。我在结论里写的是"训练顺利通过了所有早期瓶颈（step 5、25、40），跑完了 **1200+ 步**"。

**这个值留下来了**（它是一条真实存在的对齐约束，今天的仓库仍然要求 `bucket_reso_steps = 128`）。**而"它能解释那次崩溃"这个结论没有留下来。**

**后来它被推翻了。** 今天的仓库文档在这一点上毫不客气：`fix2.txt` 写着"这不是 fix1 的桶 bug"，`fix2-ex.md` 复述了两遍——"`bucket_reso_steps` 本来就是 128，latent 是 `96×128`（kanae）/ `96×160`（另一套数据），都能被 16 整除"。而在我手上的全部材料里，`fix1.txt` 是**唯一一份没有日期、没有 run id、没有 config 快照的结论**——它靠的不是证据，是记忆。这次的教训很简单，但值得写在最前面：**"跑通了 1200 步"不等于"我修好了它"**，它也可能只是那 1200 步恰好没抽中下下签。

（有意思的是，它的 dmesg 家族和我后来抓到的**完全一样**：同样是 `[gfxhub] page fault`、同样 TCP client、同样 `RW: 0x0`。只有 ring 号不同——`ring:24` 对 `ring:157`。一开始，我对着正确的日志，读出了错误的结论。）

## 第二幕 · 训练过程中开始频繁崩

> 时间：2026-09-14（fix2）、2026-09-15 → 09-16（fix3）。证据：[`../fixes/fix2.txt`](../../fixes/fix2.txt)、[`../fixes/fix2/README.md`](../../fixes/fix2/README.md)、[`../fixes/fix2-ex.md`](../../fixes/fix2-ex.md)、[`../fixes/fix3/README.md`](../../fixes/fix3/README.md)

### 2.1 第一个像样的假说：partial tile

我把栈换到 `torch 2.13.0+rocm10.0.0` / HIP `7.15.26333` 之后，它崩得更勤了。`fix2.txt` 给出了一个精确得多的假说：**这是 Tensile 的 partial tile**。

我的推理是这样的：PEFT LoRA 在 UNet 的 `to_k`/`to_v` 上对 encoder hidden states 求梯度时，会出现 `[B·231, 36] @ [36, 2048]` 这样的 GEMM（K = `network_dim`）。取 `B = 2` 时 `M = 462 = 7×64 + 14`、`K = 36 = 1×32 + 4`——两个方向都是"带余数的 tile"。于是"gfx1201 的 `MT64×64×32/64` kernel 在 `global_load_tr` 上丢掉了余数边界检查"。它给出的规避建议是：别同时用 `train_batch_size = 2` 和 `network_dim = 36`。

**然后它被同一个实验包里的数据打死了**（[`../fixes/fix2/README.md`](../../fixes/fix2/README.md)）：

- 那个"必崩组合"在真实的 188 张图数据集上**跑满了一个 epoch**（94 步，118 秒）。把每一句 caption 都补齐成 3 个 chunk、让每一步都满足 `M = 462`、`K = 36`——**还是跑满**。
- 它的前提在这份数据上根本够不到：caption 的 chunk 大小是 `tokenizer.model_max_length - 2 = 75`，而这批 caption 最长 **145** token，最多 2 个 chunk。batch = 2 时 `M` 只能是 154 或 308，**永远到不了 462**。
- 最狠的一刀是 `network_dim = 32`：`K = 32` 恰好是一整块 32 宽的 tile，**根本没有 partial K tile**——它在 step 4 崩了。

于是"避开 partial tile"作为一条规则被判死，理由只有一句：**同样的形状在一个干净的进程里跑得好好的。**

`fix2.txt` 里反倒值得留下来的是它排除掉的那些：`PYTORCH_NO_HIP_MEMORY_CACHING=1` 能撑过 5 步（代价很大，见下），而"把 TE 的 backward 和 UNet 的分开"、`TORCH_BLAS_PREFER_HIPBLASLT=0`、"只有 math 的 SDPA"、"关掉 TE checkpointing"——**全部无效**。

### 2.2 九月十四号那一夜：6/6

真正的转折出现在 2026-09-14 晚上。同一份配置，只改 seed：`seed = 1145141920` **连续 6 次崩在 step 101**；`seed = 1145141919` 跑了 7 次，7 次都活。

内核日志里的四条（同一晚，四个不同 pid）：

| Sep 14 20:17:31 | 214881 | `0x00007fd56be00000` | `0x0080113B` | ring:157 vmid:8 pasid:946 |

**其中两个细节我当时就记了下来，后来都用上了：** 两次尝试的 `rptr`/`wptr` 完全相同（3353460 / 3353739），而故障地址不同；**所有故障地址都是 2 MiB 对齐的**。

关于 seed 的机制，我算清楚了一层：

- `shuffle_caption` 的随机数取自 `cfg.seed + epoch + sha1(image_path)`，所以 tag 顺序（进而分词后的 chunk 数、进而这个 LoRA GEMM 的 `M`）依赖 seed。
- 两个 seed 的 `M` 直方图：`{462: 102, 231: 18}`（活的）对 `{462: 101, 231: 19}`（死的）。第一步出现差异在 step 96，而**死的那一步（101）恰好是一次 462 → 231 的形状切换**。

**但我在同一次会话里就给这个解释泼了一盆冷水**，这段值得原样保留，因为它定义了后面所有的实验设计：

> 形状本身并不充分：`M = 462` 占了两个 seed 大约 85% 的批次，两个 seed 绝大部分时间都待在里面。不同的是**序列**，而崩溃落在一次**形状切换**的步骤上。
> 布局是可复现的：因为形状序列由 seed 固定，分配器的排布也被固定——这就是为什么同一个 step 每次都失败。

### 2.3 决定性的一步：把采样关掉

如果"形状切换"是原因，那么只要让序列里没有切换就行——可那样就没法训练了。于是我把**采样**关掉了（`save_every_n_steps = 0`）：

> **同一份 seed、同一批形状、同一个优化器，跑满 120/120 步。**
> 采样这一段才是让分配器进入"越界正好落在未映射页上"那个状态的东西。

于是我对整件事的说法变了：

> **形状告诉你在哪里越界；真正决定那一下会不会踩空的，是周围的分配布局**——一次真实的训练、在特定的 step、配特定的 seed。

同一份证据还顺手给出了下面这张阶梯（同一 seed、同一形状，只动采样节奏）：

| 采样节奏 | 死在哪 |
| --- | --- |
| 每 30 步，768×768 样本 | step 101 |
| 每 30 步，512×512 样本 | step 90（第 3 个样本那一步） |
| 每 30 步，样本只降噪一步 | step 90（同一步） |
| 每 10 步，512×512 | step 31（第 3 个样本之后一步） |
| 每 5 步，512×512 | step 20（第 4 个样本） |
| 每 2 步，512×512 | **step 8**（第 4 个样本） |
| 每 3 步，512×512 | 活着（12 步、4 个样本） |
| 每 30 步，256×256 单步样本 | 活着 120/120（"这么小的样本什么也污染不了"） |
| 关掉 | 活着 120/120 |

这张表有两条读法：死亡落在"第 3 或第 4 个样本上，或紧随其后"；**把样本改小是把失败推早、不是推走**。另外还划出了一条很干净的边界：`flush_memory_every_step`（每步 `empty_cache`）**不管用**，`max_data_loader_n_workers = 0` 也**照死不误**（所以 DataLoader 的 forkserver 不在这个故事里）。

### 2.4 一连串"最小复现"全灭

这一段是我花掉最多算力、拿到最少正面结果、但价值最高的一节：**我把所有能想到的"更小的复现"都写了一遍，它们全部活着。**

| 夹具 | 它做什么 | 结果 |
| --- | --- | --- |
| `crash.py` | 自带一个 dim-32 的训练循环（不 import `trainer/`） | 8/8 步活着，跑三次都活。而且它和真训练器**损失值对得上**（`0.1498 / 0.1525 / 0.1633 / 0.1219` 对 `0.1498 / 0.1524 / 0.1632 / 0.1219`），`AMD_LOG_LEVEL=4` 显示两者碰的是**同样的 67 个 Tensile kernel**，第一步的 5735 个分配尺寸也**一一相同** |
| `repro.py` + `trial.py` | 无模型：真 PEFT LoRA GEMM，扫 M / rank / dtype / 分配器扰动 / 层数 / 常驻量 | **0 / 40** 崩 |
| `repro_unet_sweep.py` | 真 SDXL UNet + LoRA，真桶 latent | **0 / 7** 崩 |
| `repro_joint.py` | 真 UNet **和**两个 CLIP 文本编码器一起 backward（`fix2.txt` 说这个组合必崩） | M=231、M=462 都活着 |
| `repro_min.py` | 独立 diffusers + peft + torch 循环 | 5 种变体，**没有一种崩** |

这一节的结论可以压成一句话：**"这个 fault 是这个进程的分配历史的属性，不是这一步的属性。"**

我顺手也把环境变量这一层测清了（12 步窗口，同一份 latent 缓存）：

| 变量 | 结果 |
| --- | --- |
| 什么都不设 | step 4 崩 |
| `HSA_SVM_GUARD_PAGES=0` | 活着 12/12 |
| `PYTORCH_NO_HIP_MEMORY_CACHING=1` | 活着 12/12 |
| `GPU_SINGLE_ALLOC_PERCENT=50` | step 4 崩 |
| `HIP_MEM_POOL_SUPPORT=1` | step 4 崩 |
| `HSA_DISABLE_FRAGMENT_ALLOCATOR=1` | step 4 崩 |
| `HSA_DISABLE_CACHE=1` | step 4 崩 |
| `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` | 第一步 loss 就是 `NaN`，训练器连序列化都过不去（不能用） |

**关于 `HSA_SVM_GUARD_PAGES=0`**——它在后面的故事里反复出现，定位必须一次说清：它不是修复，它关掉的是**探测器**。ROCm 默认给 SVM 分配后面留一页不映射的 guard page（那个变量默认是 1），把它关掉之后，越界读落在已映射内存上、静默读完。它在本次追查里是**极好的探针**（正因为关掉它之后损失和 LoRA 张量逐字节不变，我才能断言"读本身是惰性的"），但它**永远不该出现在生产环境**：它会把那个进程里每一次越界读都一并变成静默行为。

`PYTORCH_NO_HIP_MEMORY_CACHING=1` 是另一回事：它让每个张量各拿一次 `hipMalloc`，于是没有哪个操作数正好卡在缓存段的边缘。有效，但慢 2.2–2.9 倍（2.9 s/it 对 1.12 s/it），而且它改变的是分配器行为，遍布全局。**这是缓存，不是修复。**

### 2.5 关于"逐字节不变"这件事，以及我差点骗过自己

我做了一次完整性对照：`cached` 对 `no-hip`（seed 1145141919）**120/120 步损失逐字节相同、2208 个 LoRA 张量在 step 30/60/90/120/final 全部逐字节相同**；dim 32 的 12 步对照同样全等；甚至那个"崩在第 101 步"的运行与活下来的运行，**在它们共有的 101 步里损失与张量全部相同**。

（同一批实验也暴露了两个陷阱，都记在案：**两次同配置的运行不会得到相同的 latent 缓存**——6 个 latent 里只有 1–4 个能和另一次对上，因为 MIOpen 每次进程会挑不同的卷积算法——所以任何"逐字节对比"都必须在固定缓存的前提下做；以及**第一版 seed 网格的种子只写在行标签里、没真正传进行里**，于是制造出一个"换个样本 seed 就能把活的变成死的"的漂亮结果，纯属标签错误，后来被 `repro_real.py` 用"标签里的 seed 和实际要跑的 seed 不一致就拒绝启动"堵死。）

### 2.6 然后它把第一步也吃了：fix3

> 时间：2026-09-15 23:16 → 2026-09-16 00:30。证据：[`../fixes/fix3/README.md`](../../fixes/fix3/README.md)

`fix2` 那套实验是在 `2.13.0+rocm10.0.0` 上做的。为了对照，我把栈改回 `2.12.0+rocm7.14.1`——然后发现**打包好的 fix2 复现包在这套栈上不崩了**，我自己当时线上那份配置也顺利跑了 700+ 步。

我差点就把"回退栈"当成答案。

fix3 做的事是：**拿仓库里 commit 的那份 `config.toml`（`network_dim = 48`、`train_batch_size = 2`、640 张图）在这套栈上跑一遍**——结果它**死在第一个训练步，每一次，约 15 秒**。改了 seed 也一样（seed 1145141919：9 次 9 崩，`steps_reached` 全是 0）。重启后依旧。

于是 `doc/troubleshooting.md` 里"这套栈免疫"的说法被我撤回：它改变的只是**抽签中不中**，而不是**kernel 会不会越界**。

fix3 最有价值的一件产出是 `probe_op.py`：它把自己塞进训练器的位置，把每一步启动的每个 GEMM 连同形状、forward/backward 标签都记下来。崩溃前最后一行是：

```
OP 8344 backward aten.mm.default [[48, 308], [308, 1280]]
Dispatch Header = 0xd02 (type=2, …), setup=3
grid=[2560, 1, 1], workgroup=[128, 1, 1], group_seg_size=1638
Memory Fault Error … faulting addr: 0x7f2d68800000,
  kernel: Cijk_…_MT64x128x16_…_ISA1201_…
```

这是个**文本编码器 LoRA 的 A 权重梯度**（`grad_A = grad_outᵀ @ input`），它的三个维度各有身份：`M = 48 = network_dim`（秩）、`K = 308 = batch(2) × 序列长(154)`、`N = 1280 = text_encoder_2` 的 hidden size。同一步的上下文是 `8331 lora_A input grad` → `8332 grad_A`（死在这里）→ `8333 lora_B input grad` → `8334 base layer input grad`。

fix3 还做了一件很有说服力的事：它把桶和这一步的 GEMM 分开了。

| 桶 | latent | batch 2 时的 `M` | rank 24 | rank 48 | rank 64 |
| --- | --- | --- | --- | --- | --- |
| 1280x768 | 160x96 | 308 | ok | **崩** | ok |
| 512x1920 | 64x240 | 308 | ok | **崩** | ok |
| 512x2176 | 64x272 | 308 | **崩** | **崩** | ok |
| 1408x768 | 176x96 | 462 | ok | ok | ok |

关键在于：**桶根本不出现在这个 GEMM 里**。文本编码器只看 `batch × sequence`，它从来看不见图像。所以桶只可能通过分配器起作用——UNet 为这个桶分配的激活量决定了文本编码器那些 LoRA 缓冲会不会正好贴着一个空洞。（而 `M = 308` 本身也不充分：`(1280x768, 24)`、`(1280x768, 64)`、`(512x1920, 24/64)` 和致命的格子行数相同，却活着。）

46 次 fault 里 **44 次是同一个 855 字符的 kernel 名**，两次例外是 `network_dim = 36` 落在另一个解法（`MT64x64x64`）上。没有一次崩溃发生在 `M = 154` 的步骤上。

## 第三幕 · 把 torch 剥掉

> 时间：2026-09-15 夜 → 09-16 凌晨。证据：[`../fixes/hip1/hip1.md`](../../fixes/hip1/hip1.md)、[`../fixes/hip1/source-trace.md`](../../fixes/hip1/source-trace.md)

到这里，"这是我自己的代码的问题"这个可能性还很大：也许是 torch 的缓存分配器，也许是我的数据集/掩码/循环，也许是 MIOpen 选了个坏算法。

于是，我决定剥离掉整个 PyTorch 栈，直接写一个 HIP 程序（`fixes/hip1/launch_fault_kernel.hip`）去复现它。这个程序的做法很直接——

1. 它从磁盘上取 hipBLASLt 自己装着的那一份 code object（把一个 `.co` 文件用 `clang-offload-bundler` 解开，得到里面的 ELF），**整个进程只加载这一个文件**；在这个文件里它只查**一个** kernel，名字就是源码里那个 855 字符的字面量。
2. 手工搭那 144 字节的参数块（`static_assert(sizeof(Args) == 144, "the metadata says kernarg_segment_size is 144")`），走 `hipModuleLaunchKernel` 的 raw-buffer 形式（hipBLASLt 自己也是这么发的，ABI 布局由我来定，而不是让 runtime 去猜）。
3. **给操作数摆位置**：每个操作数用 VMM 预约 `mapped + 4096`，映射 `ceil(size/4096)×4096` 字节，然后**把 kernel 要用的那块放在映射的末尾**——于是操作数的最后一个字节就是映射的最后一个字节，紧跟着的那页预约了但从不映射。**不管越界多少，只要越过边界就必然撞上它。**

这个实验的结果直接决定了后面的研究方向：**一个单进程、没有 torch、没有 hipBLASLt、没有 MIOpen、没有数据集、没有分配器邻居的程序，居然也当场崩了。**

随后，因为怀疑可能是我自己搭的那个参数块有问题，我通过第二条路线（`launch_fault_via_rocblas.hip`）把这个变量也去掉了：直接用 `rocblas_gemm_ex` 调 `m 1280 / n 48 / k 308`，让库自己去选解法（它选了 `sol-idx = 107020`），同样把操作数摆在页边界上——**fault 落在 B 那块 29,568 字节操作数的 guard page 第一个字节上**。

这两条路线一共留下三条独立的证据，它们把责任钉死在"库自己那份预编译 kernel"上：

**（一）eBPF 看到的加载链**（6 个 uprobe；注意这里有个坑：进程的**线程名**是 `pt_autograd_0`，所以按 `comm == "python"` 过滤会什么都看不到——我的前两次尝试就是这么白跑的）：

```
hipModuleLoad        comm=pt_autograd_0  file=…TensileLibrary_BB_BB_…_l_Ailk_Bjlk_…_gfx1201.co -> err=0
hipModuleGetFunction … err=500 (hipErrorNotFound) ×4  → … err=0
hipExtModuleLaunchKernel … grid=2560,1,1 -> 488 dispatches
```

这是 hipBLASLt 的懒加载模式：先问所有已加载的模块有没有这个 kernel，都没有才去加载那个有的文件——**所以这个 `.co` 在运行中很晚才出现，而且只出现一次**。（后来的单位修正：`grid=2560,1,1` 是 work-item 数，等于 20 个 workgroup。）

**（二）故障日志自己带着证词。** ROCr 的 dump 里有 `kernel_obj`，也就是硬件执行的那个 kernel 描述符地址；描述符的虚地址是 `0x282380`，四次记录的差值全是 2 MiB 对齐：

| 运行 | `kernel_obj` | 减去 `0x282380` |
| --- | --- | --- |
| fix3 实跑（2026-09-15） | `0x7f2cd2682380` | `0x7f2cd2400000` |
| eBPF 第 2 次 | `0x7f3f92082380` | `0x7f3f91e00000` |
| eBPF 第 4 次 | `0x7f77f5882380` | `0x7f77f5600000` |
| hip1 单进程复现 | `0x7f8556a82380` | `0x7f8556800000` |

最后一行是最强形式的论证：**一个只加载过这一个 code object、只发射过这一个 kernel 的进程，仍然崩在同一个描述符上。**

**（三）排除法。** rocBLAS 自己那份 gfx1201 懒加载库里 `"solutions": []`，它的 67 个 code object 里没有一个含 `Cijk_`/`UserArgs` 字符串；MIOpen 的缓存里也没有这个名字（它的 kernel 叫 `Im2d2Col_v2` / `batched_transpose_*`）；torch/torchvision 的包里也没有。而且**这不是 JIT 或缓存的产物**——这个名字在 run 开始之前就已经躺在出厂 `.co` 里，运行只是读了它。

我顺手把影响面也数了一遍：gfx1201 上 hipBLASLt 装的 4 个纯 bf16 Tensile 库，解出来 **2105 个 kernel，1830 个可以发射**（275 个被跳过，原因清一色是 `globalSplitU > 1`，需要 split-U 工作区），按布局分 372 / 406 / 303 / 749。另一条独立的路线（`sweep_gemm_shapes.hip`，让 hipBLASLt 自己选解法、扫形状）跑出 **234 次 fault、覆盖 15 个不同 kernel，全部落在两个 `Bjlk` 布局的库文件里**。

单看那一个 kernel 的形状阶梯（围绕它自己的 macro tile 造的 10 个形状，pad 0）：`clean 4 / wrong 0 / fault 6`——**唯一干净的是那个"正好填满 tile"的形状**（`128x256x64`，K = 4 × `DepthU`，crc `0xe4a70c8f`）。而它的距离梯子只有三行：

| `--pad` | 结果 |
| --- | --- |
| 0 | **崩**（落在 B 的 guard page 第一个字节；B = 64×308 = 39,424 字节） |
| 4096 | 干净，crc `0x4ec0d5e7` = 精确参考值 |
| 65536 / 262144 | 干净，crc 同上 |

**越界超过 0 字节、不超过 4096 字节，而且读到的数据不改变 D。**（`fix2` 时期的数值口径是"最多 4 KiB 越界，杀死训练的那个形状算下来是 2 KiB"。）

## 第四幕 · 为什么"多读一点"是不可避免的

> 证据：[`../fixes/hip1/source-trace.md`](../../fixes/hip1/source-trace.md)、[`../conclusions/bf16-kernel-overrun.md`](../../conclusions/bf16-kernel-overrun.md)

第四幕要说的只有一句话：**只要矩阵的行是紧密排列的，读到原本不需要的东西就不可避免；剩下的问题只是多读的地方合不合法——而实验表明，它完全可能不合法。**

### 4.1 读是必然的

我把那个 kernel 反汇编了一遍：里面一共 120 条 load，其中 **36 个是 `global_load_tr_b128`**（每次 16 字节的转置 load），分布在 4 个位置（每个 9 条）——**这个 kernel 对 A/B 操作数的每一次读取，都是 16 字节的向量化转置 load**。而这 4 个位置里**只有最后一个**前面有边界钳位：

```asm
0x56FFF0  v_min_i32_e32 v64, v148, v64                 // 钳位
0x56FFF4  global_load_tr_b128 v[76:79], v64, s[48:49]  // A，16 字节
0x570060  v_min_i32_e32 v65, v148, v65
0x570064  global_load_tr_b128 v[84:87], v65, s[52:53]  // B（×8）
```

（那个 kernel 打进来的形状是 `M = 48`、`N = 1280`、`K = 308`。`K = 308 = 19×16 + 4`，所以最后一块尾 tile 一定要取进来；`M = 48 < 64` 的 macro tile，所以第 48…63 行也会被取进来。）

这三处越界各自的量级是这样的：

| 位置 | 为什么 | 最坏情况 |
| --- | --- | --- |
| A 的 K 尾 | `K = 308 = 19×16 + 4`，最后一行要取 l = 308…319 | 12 个元素，**24 B** |
| A 的 M 边 | `M = 48 < MT64`，i ≥ 48 的行也被取 | 16 行，**9.6 KB** |
| B 的 K 尾 | B 是 `[K,N]` 存储，l = 308…319 是整整 12 行越界 | **30 KB** |

实测：hip1 的单进程复现崩在 **A 的映射末端之后的第一批页**里（6 次重复里 5 次落在 guard page +4096、1 次落在 guard page 本身；`M` 边的越界跨度是 9,856 B ≈ 2.4 页，ROCr 报的是 warp 先撞上的那一页）。而 rocBLAS 那条路线（库自己的描述符，m=1280/n=48）算下来最远读到 158 字节，落在第一页里。**所以可复现的断言只能说"操作数末端之后、头几页之内"。**

### 4.2 ISA 保证不了合法

生成器**知道**自己在越界读，而且它是"被允许"的——只要那条假设成立：

```python
asmCaps["HasPartialOOB"]   # KernelWriterAssembly.py:10214-10215
```

而 `hardware_caps.hpp:96` 把它定义成"**除了 gfx1250 之外的所有 ISA**"：

```cpp
checkNotInList(isaVersion, {{12,5,0}})
```

gfx1201 在这个列表里，所以生成器认为"超出边界的那部分访问会被硬件丢掉"，于是它敢发这条宽 load，并且**为了这个原因专门预先把目标寄存器清零**（生成器注释原话：`set to zero to avoid unexpected value`）。

**但这个假设要靠描述符来承载，而这条路径上的描述符没有 bound 字段。** 一个 MUBUF 的 `buffer_load` 有记录数（record count），硬件可以据此裁掉越界部分；而这里用的 `global_load_tr_b128` 只有 **2 个 SGPR 的 64 位地址操作数**，**没有任何 bound 字段**——在这条路径上，**没有任何东西在执行那条假设**。

这就是"ISA 保证不了合法"的确切含义：**ISA 的能力声明是有条件的，而条件没被满足，也没被检查。**

### 4.3 kernel 也保证不了

那 kernel 自己呢？它唯一的保险就是上面那条 `v_min_i32`，出自生成器的 `KernelWriterAssembly.globalReadGuardK`（`:10207`），它的注释写着：

```
"truncated load: clamp GRO to legal range"
```

它的三个性质，每一个都致命：

1. **它钳的是地址，不是访问窗口。** `VMinI32(offsetVgpr, maxGroVgpr, offsetVgpr)` 限制的是这次 16 字节访问**从哪里开始**；访问宽度压根没进这个计算。所以一个"关于最后一个元素是对的"的上限，仍然允许这次访问结束在它之后 **最多 14 字节**。
2. **上限来自问题的 K 余数与 tile 几何，不来自操作数的大小。** 那段 `isTr` 代码里**没有任何一处**提到"分配了多少字节"。
3. **越界的数据是事后丢弃的，不是事前避免的。** 尾循环里 `v_cmp_ge_i32 s66, v149, s12` 拿 K 边界比一下，`v_cndmask_b32_e64 …, 0, s66` 把寄存器换成零——**可是读已经发生了**。

所以呢？**kernel 只是个算数的，它没法凭空给用户变出一个合法页框。**

### 4.4 三个"修生成器"的候选，全部实测失败

我真的写了三个候选补丁去改那段钳位，然后拿它们跑了那套 10 形状阶梯：

| 候选 | 做什么 | 结果 |
| --- | --- | --- |
| A | 上限再减一个访问宽度（14 B） | 训练器那个形状 CLEAN，**但阶梯上 10 例里 7 例算错** |
| B | 超过上限的读改成读块首 | 仍然 fault（10/10 干净，crc 精确——但是"读块首"是错的语义） |
| C | 上限 = min(现在, 操作数剩余字节 − 一个访问) | CLEAN，**同样 7/10 算错**，且 crc 与 A 相同 |

原因写出来很朴素，也很根本：**那些跨过操作数末端的读，有一部分是在界内的，而界内那部分是尾块需要的数据。** 所以这次访问**既不能收窄**（会丢掉需要的数据）**也不能封顶**（地址侧封不住宽度）。生成器补不了这个洞。

`source-trace.md` 用一句话给这一节收尾，我认为那是整份材料里最重要的一句：

> **要么操作数自带余量，要么这个解法不该被选中。**

——这正是后面所有工作的分界线；我后来选了前半句。

## 第五幕 · 改源码这条路

> 证据：[`../fixes/hip1/gltr-asem-rule.patch`](../../fixes/hip1/gltr-asem-rule.patch)、[`../fixes/hip1/hip1.md`](../../fixes/hip1/hip1.md) §13

既然生成器那侧的钳位补不上，我就顺着"要么这个解法不该被选中"这句话往下走：**用厂商自己的机制，把会越界的解法排除掉。**

厂商确实有这么个机制。ROCm 源码里有一行现成的惯例（注释写着"用 `AssertSummationElementMultiple`（在谓词里就是 `BoundSizeMultiple`）排除失败的 tail-loop 情形"）：

```python
state["AssertSummationElementMultiple"] = max(state["AssertSummationElementMultiple"], state["DepthU"])
```

它本来只用在两种布局上；我把它扩到了 GLTr 布局（`Solution.py`，10 行）：

```python
    if state["enableGLTrA"] or state["enableGLTrB"]:
        state["AssertSummationElementMultiple"] = max(state["AssertSummationElementMultiple"], state["DepthU"])
```

我把这句话写进了补丁头的注释：`实测：它把选择从 DTV 解法上移开了，但没有止住崩溃`。测量结果如下：

- 这个家族 473 个解法里，**157 个被改名**（各自的 `ASEM` 变成自己的 `DepthU`）。
- 运行时**确实**不再选 DTV 解法了（日志里 `…ASEM1…DTVA0_DTVB1` 变成 `…ASEM1…DTVA0_DTVB0…`）。
- **但崩溃没有消失：12/12 全部 fault**（4 种 epilogue 变体 × 3 种库配置：出厂版、重建无谓词版、重建加 `BoundSizeMultiple` 版）。
- 原因也看清楚了：**被改名的那个 kernel 仍然有 36 条转置 load 和 5 个 tail 标签**——`ASEM → NoTailLoop` 并没有把那次被钳位的读去掉。也就是说，这个家族**至少有两个 over-reader**：DTV 的，和替补上来的非 DTV 那个（后者用 1 元素的 `buffer_load`，越界的方式和 GLTr 的钳位无关）。

另外还有一个更结构性的理由，说明这条路走不通：**这条规则要拒掉这个家族 473 个解法里的 157 个**，而厂商自己的调优表里，它覆盖的 **7768 个问题没有一个受影响**——其中 6345 个由 DTV 解法拿下，而**这些问题的 `K % DepthU` 全部为 0**。换句话说：**会崩的这个形状，从来没进过厂商的 benchmark 集。** 这也顺便解释了为什么它从来没被调优掉。

至于部署，就算这条规则有效，代价也很硬：

- 运行时装的是**预编译的 `.co`**，所以必须重建，而且 `.co` 和 `.dat.zlib` **必须一起换**（运行时按 `.dat` 里的名字选 kernel，参数块描述也在同一条记录里）。
- 部署要靠 `HIPBLASLT_TENSILE_LIBPATH` 指向另一棵库树，而它**必须指向"装着那些文件"的那一层目录**（loader 会把文件名拼在后面；指到上一层，hipBLASLt 直接回 `HIPBLAS_STATUS_INVALID_VALUE`；指到一个不存在的路径，日志里会出现 `hipModuleLoad failed: /nonexistent/Kernels.so-000-gfx1201-xnack-.hsaco`）。
- 源码在仓库外的一个 checkout 里，改的是**一个文件**（外加两个必须的 untracked 符号链接）。
- 单文件重建（427 个 kernel）要 **15 秒**，重建保真度没问题（427 = 427，未改动的重建能在同一个地址上复现同一个 fault）——**但性能代价一次都没测到**：凡是被这条规则改掉选择的形状，都先崩了，运行根本活不到打时间行。

由此我得出一个结论：**Patch 源码这条路径的可行性极低，我不打算走它。**

> 一处更正：这份材料的早期版本里写着"这条规则确实去掉了越界读（10/10 无 fault）"。那句话不成立——当时那个 build 同时还带着候选 C 的生成器实验，零 fault 是候选 C 带来的，与这条规则无关；把生成器恢复成原版之后，改名后的 kernel 在同样那六个形状上照样 fault。所以这句话已经撤回。

## 第六幕 · 换个角度：给 kernel 一块合法的尾巴

到这里，我对整件事的认识是这样的：读是必然的，合法性没人保证，而修 kernel 那条路被三件事同时堵着——**钳位补不了、解法躲不掉（家族里至少两个 over-reader、而厂商的调优表里根本没有这个形状）、重建加部署的成本与风险都不可控。**

于是我把问题重写成了一句人话：

> **既然不能让 kernel 别读，那就让它的读落在一块存在的内存上。**

这句话展开就是两个角度：

**角度一：ROCm 架构层。** 这条路径要求 ROCm 自己保证：会参与这类指令运算的内存，尾部一定存在这样一个合法空间。而这恰恰暴露了当前 ROCm 内存管理体系的一处架构缺陷：**guard page 是它自己设计进去的**（`HSA_SVM_GUARD_PAGES` 默认 1），**2 MiB granule 的取整也是它自己的规则**——一个"整颗 granule 刚好用完"的分配，它的下一个字节就是未映射页，而系统里没有任何一层承诺过要给这种分配留余量。要在这条路径上把事做对，就得动内存管理架构本身：要么让分配器在尾部保留一页，要么让这类指令的语义在驱动层被兜住。**这大概也解释了 AMD 为什么迟迟不解决——这不是一个补丁，这是一次架构手术。**

**角度二：调用方层。** 我在申请内存的时候就多要一个保留页，**这才是投入产出比最高的一条路**：它不需要任何人批准，不需要动 ROCm，也不需要动 kernel，只要在"内存交出去"和"kernel 拿到它"之间的那一层加上一句。我选了这一条。

在动手之前，有两种实现方式摆在面前：

| 方式 | 好处 | 代价 |
| --- | --- | --- |
| 改 torch 的内存池代码 | 从源头解决，一次做完 | 要维护 torch 的分支/补丁，跟随上游升级；只覆盖 torch 的分配路径 |
| **二进制 hook（`LD_PRELOAD`）** | 不碰 torch、不碰 ROCm、不重新编译任何东西，可随时开关 | 只拦得到跨 PLT 的调用；属于外部工具 |

我选了后者。于是有了 **amdfq 计划**——这个名字的来历就不翻译了，它的全称是"全程 AMD FUCK YOU"，缩写正好是这四个字母。冷静下来看，这个名字记录的是我当时的情绪：**我认输了，但认得还算有尊严——我不再试图让 AMD 的 kernel 变对，而是把它围起来。**

## 第七幕 · pad-16，和它的控制组

> 时间：2026-09-17。证据：[`../amdfq.md`](../../amdfq.md) §9–§10

第一版补丁小得可以贴在名片上：`hipMalloc` 向 runtime 多要 **16 字节**，然后把原来的指针还给调用方。

```c
hipError_t hipMalloc(void **ptr, size_t size) {
    size_t padded = size <= SIZE_MAX - 16 ? size + 16 : size;
    hipError_t result = real(ptr, padded);   /* 调用方仍然只看得到 size */
    ...
}
```

**为什么 16 字节就够了，这中间有个不显然的地方。** 真正起作用的东西不是那 16 字节，而是 runtime 的**2 MiB granule 取整**：一个请求量恰好是 granule 整数倍的分配，本来会正好用光它那一颗 granule、下一个字节就是未映射页；加上 16 字节之后它装不下了，runtime 只好**再reserve 一整颗 granule** 给它。于是那个边界后面多了一整颗 2 MiB 的已映射内存（地址空间和显存都有）。**代价就是这一整颗。**

`hipFree` 不需要知道这些（它只拿指针），所以调用方一侧完全无感：同一个指针、同一个 size、同一份布局。

### 7.1 控制组：把"是 pad，不是 hook"钉死

一个 `LD_PRELOAD` 对象本身就会改变分配布局，所以我必须把"插桩"和"加 pad"分开，做法是做一个只差**一行**的构建（`AMDFQ_VRAM_PAD 16 → 0`，`diff -r` 确认那一行以外没有别的）：

| 运行 | 预加载 | pad | 结果 |
| --- | --- | --- | --- |
| `lllj_20260917_041147` | — | — | step 10 abort；`[gfxhub] page fault` 04:12:31，pid 71023 |
| `lllj_20260917_045346` | — | — | step 10 abort；fault 04:54:10，pid 85072 |
| `lllj_20260917_050031` | `libamdfq.so` | 16 | 14 步，无 fault，手动停 |
| `lllj_20260917_050412` | `libamdfq.so` | 16 | **41 步，exit 0，`status=finished`** |
| `lllj_20260917_050950` | `libamdfq.so`（pad-0 构建） | **0** | **step 10 abort**；fault 05:10:16，pid 96771 |

最后一行就是控制组：**它插桩但不加 pad，于是照样崩**。另外三条证据把"巧合"这个选项堵掉了：

- **同一份运行，不是相似的一份。** 控制组前 4949 条 `hipMalloc` 的尺寸与加过 pad 的那次**逐条相同**，从第 4950 条开始分叉——因为控制组那时已经死了。
- **速度没变。** 控制组 10 步的中位数 1.160 s/step，加 pad 那次 40 步是 1.154，无 hook 的一次是 1.159。插桩没有扰动时序。
- **同一个 fault 回来了**：同一个 step（10）、同一个签名（`0x00801031`、TCP client）、而且 abort 的运行**没有 `fini` 摘要**（进程被 `SIGABRT` 带走，不是干净退出）。

### 7.2 代价：很贵，贵到不能接受

我从加过 pad 的那次自己的日志里重放了 malloc/free 流，按 `round_up(size + 16, 2 MiB)` 给每个活块记账：

| | 不加 pad | 加 pad | 代价 |
| --- | --- | --- | --- |
| 全run 峰值常驻 | 12,244 MiB | 14,778 MiB | **+2,534 MiB（1.207×）** |
| 稳态训练（15–55 s 的 5 s 窗口） | 11.2–12.2 GiB | 13.6–14.7 GiB | 中位 **+2.49 GiB** |
| 那一刻整卡用量 | — | 15,925 MiB / 16,304 MiB | **只剩 379 MiB** |

原因是 granule：**14,038 次 `hipMalloc` 里有 14,032 次要的是 granule 的整数倍**（其中 10,972 次是缓存分配器的 2 MiB 小池段）。峰值时刻大约 1,255 个块活着，1,255 × 2 MiB 就是那 +2.5 GiB。唯一不受影响的尺寸类是 25 MiB（6 次调用）——因为它本来就没对齐。（累计字节数在这里毫无意义：整个 run 要了 172.15 GB，其中属于 pad 的只有 **224,608 字节**。）

**注意这 +2.5 GiB 是"这个进程还能用的显存"少掉的部分，不等于驱动计数器会涨的幅度。** 第八幕会说明后者只涨了 0.3 GiB，以及为什么"少掉的 2.4 GiB"仍然是真金白银——对 ROCr 自己的客户而言。

时间上一分钱没花（1.154 对 1.159 s/step）。**但 +2.5 GiB 在 16 GB 的卡上是要命的**：峰值不在训练步，而在 run 末的 checkpoint 保存，那一刻离满只剩 379 MiB。

所以第七幕的结论可以压成一句话：**机制成立，设计不合格。** 一个"每个活块买一颗 granule"的方案，价格是这张卡剩余的绝大部分余量。**我必须把价格降下来；至于怎么降，就是后面两条路线的事。**

## 第八幕 · 内存去哪了

> 时间：2026-09-17。证据：[`../amdfq.md`](../../amdfq.md) §11、[`live-data.md`](live-data.md)（四轮的中文原始记录，663 行）

这一幕是整篇里我被自己骗得最惨的一段。

事情的起因很无辜：我想给"降价格"这件事定一个基线，于是去量 pad 到底花了多少钱。量着量着就发现——**同一个进程，三本账互相打架。**

| 仪器 | 怎么读 | 覆盖谁 |
| --- | --- | --- |
| 驱动计数器 | 进程外读 `/sys/class/drm/card1/device/mem_info_vis_vram_used` | 驱动记到显存上的每一个 BO，不管是谁的 |
| HIP ledger | 进程内 `hipMemGetInfo` | runtime 对自己客户申报的用量 |
| hook 活表 | 我在三个 hook 上自己记的请求字节 | 只覆盖 interpose 到的那三个门 |
| （后来加的）BO dump | `amdgpu_vm_info`，逐进程 | BO 对象本身：大小、状态、域 |
| （后来加的）第三方客户端 | 一个进程里没有 ROCr 的 Vulkan 程序 | 不是 ROCr 客户的人能拿到多少 |

而 §10.3 那个 **+2,534 MiB 只是"按请求量重放"算出来的模型**——模型和账本不是一回事。这三本账必须先被摆平，否则"路线二到底省了多少"根本无从谈起。

### 第八幕 · 先把"应该是什么样"算出来，再看现实怎么打脸

动仪器之前，我先把直觉算清楚——**后面所有的困惑都来自这个直觉，所以它必须先被写成一个可以被检验的假说。**

pad 一旦非零，每一笔请求都不再是 2 MiB granule 的整数倍了，runtime 只好为它多留一整颗 granule。冻结那一刻有 **1,213 个活块**本来就正好落在 granule 边界上，于是：

```
1,213 × 2 MiB = 2,426.0 MiB
```

**这就是"16 pad 应该比 0 pad 多占的显存"。** 它从请求量直接推出来，不依赖任何仪器；而这 2.4 GiB 既然是真的多占了，**每一本账都应该显示它**。

而现实是这样的（两列干净数据来自第二轮，也就是纯 HIP 回放、没有 hook 也没有 torch；第一轮那个戴着 hook 的训练进程给出同样形状——11,895.3 → 12,210.9，差 +315.6——但它的 ledger 列撞在振荡相位上，做不了这个算术）：

| 仪器 | 0 pad | 16 pad | 差 | 相对"应该多 2,426 MiB" |
| --- | --- | --- | --- | --- |
| HIP ledger | 9,302.0 | 11,728.0 | **+2,426.0** | 分毫不差 |
| 驱动计数器 | 11,402.0 | 11,718.0 | **+316.0** | 只有预期的 **13%** |
| 进程地址空间（renderD128） | 11,334.0 | 11,650.0 | **+316.0** | 同上 |
| BO 总量（第五轮才加的仪器） | 12,267 | 12,576 | **+316–317** | 同上 |

**账本说"确实多了 2.4 GiB"，驱动说"只多了 0.3 GiB"，中间差 2,110 MiB。** 这就是"账对不上"的第一形态。

接下来这一步是整幕的关键：**我不能急着说"驱动瞎了"，而要把它当成一个正经假说**——它有自己可检验的预言，而且它的预言方向和另一个读数的正好相反：

| 读数 | 它在说什么 | 预言 0 pad 的计数器 | 预言 16 pad 的计数器 |
| --- | --- | --- | --- |
| **A：驱动瞎了** | 驱动没看见"每个块多要的那一颗 granule"，只看得到我确实申请的东西 | ≈ ledger 的 **9,302**（它看不见任何额外的东西） | 也 ≈ **9,302**（ledger 涨的那 2,426 它全漏掉） |
| **B：账上本来就有幽灵** | 驱动是诚实的，只是 0 pad 时账上本来就挂着约 2.1 GiB——驱动看得见、而 ledger 不承认的内存 | ≈ 9,302 + 2,100 = **11,402** | ≈ 11,402 + 2,426 − 2,110 = **11,718** |

实测：**11,402.0 / 11,718.0**。读数 B 命中（差 0.4 MiB，远小于计数器自身约 15 MiB 的量子化），而读数 A 在 0 pad 那一格就已经差了 2,100 MiB——**如果驱动真是瞎的，我应该在 0 pad 和 16 pad 都看到贴着 9.3 GiB 的读数，可它们都在 11.4 GiB 以上。**

**"驱动看到了什么不该看到的东西"这个直觉是对的，但"不该看到"要说准确一点：它看到的不是幻觉。** 0 pad 时多出来的那 **+2,100.4 MiB**（`2,202,370,048 B`）在进程地址空间里对应 **1,925 个恰好 2 MiB 的映射**，而 ledger 记账的活块里只有 869 个是恰好 2 MiB——**中间约 1,055 个 2 MiB 映射不属于任何一笔活分配**。这个数有三条独立佐证：

- `计数器 − ledger = 2 MiB × 无主映射 − 21.4 MiB` 在十一个检查点里成立十个（第三轮）；
- BO dump 把它们数成 **约 1,055 个真实的 2 MiB BO（2,110 MiB）**（第五轮）；
- 第三方进程**拿不到它们**（第四轮）——所以既不是页表预留，也不是记账幻觉。

于是真正发生的事可以一句话说清：

> **不是"我多买了 2.4 GiB 而驱动没看见"，而是"不加 pad 的时候，账上本来就挂着约 2.1 GiB 谁也没申请的幽灵显存——驱动如实记账、ROCr 真实持有、我的分配一个都不指向它、外人也拿不到；pad 让几乎每次申请都不再是 granule 的整数倍，那套对齐的 2 MiB 分配模式不再出现，幽灵也就不再被申请"。** 一进一出：`+2,426 − 2,110 = +316`，正是驱动从 0 pad 到 16 pad 只动了 0.3 GiB 的原因。

三条可能被拿来搅局的替代解释，我顺手排除了：

- **"多出来的 2 GiB 是 hook 自己的开销"**：不是。pad 设成 0 的 hook 在行为上是纯观察者（`padded == size`，4949 行一条不差），而它自己的脚印是一个**常数**——把训练进程与纯回放逐档对齐，外部 ledger 的偏移是 530.00 MiB、renderD128 是 432.2 MiB、计数器是 492.57–492.88 MiB，**四档逐字节相同**。顺带一个漂亮的核对：训练进程 0 pad 的计数器 11,895.3 减去这个常数 = **11,402.4**，正是纯回放单独跑出来的 11,402.0。
- **"是 torch 的运行时"**：它在这个常数里，且同样不随 pad 变化。
- **"驱动把页表算进显存了"**：BO dump 里 `Kernel PT/PDs` 在每个 pad 上都只有 3.9–4.2 MiB，比那 2.1 GiB 小三个数量级。

**哪一步我没有验证**：pad 为什么会让那套对齐的 2 MiB 分配模式（连同那约 1,055 个 BO）不再出现——这一层机制我没有直接测量，池子本身的用途也还是开着的（见尾声）。我验证的是**现象之间的算术**：幽灵在 0 pad 时存在（第四、第五轮各自独立证明），在非零 pad 下不存在（地址空间与 BO 两侧都只剩个位数），而两本账的差正好等于它。

### 第八幕 · 第一轮：四个 pad 冻在同一个位置

**做法是这样的**：我让 trainer 在 step 5 末尾 `SIGSTOP` 自己（桩插在 `trainer/loop.py`，实验后已撤销、与 HEAD 一致），四次只改 `AMDFQ_PAD_BYTES`（0 / 16 / 64 B / 1 MiB）。四次都停在同一个位置（`state.json` 的 `training.step = 4`、step 4 的 `loss = 0.1005521` 四次相同），进程**冻着不退出**，于是两个口径都能在静止态上读。

分配历史**逐字节相同**：`hipMalloc` 2,994 次、`hipFree` 1,775 次、活块 1,219 个 / `9,661,579,264 B`；run id `lllj_20260917_202744` / `_203050` / `_203412` / `_204138`；冻结时刻（`CLOCK_MONOTONIC`）47527.2 / 47713.1 / 47914.9 / 48360.9。

| 项（MiB） | 0 pad | 16 pad | 64 pad | 1 MiB pad |
| --- | --- | --- | --- | --- |
| hook 活表：活块 / 请求字节 | 1,219 / 9,214.0 | 1,219 / 9,214.0 | 1,219 / 9,214.0 | 1,219 / 9,214.0 |
| 回放：Σ round_up(size, 2 MiB) | 9,220.0 | 9,220.0 | 9,220.0 | 9,220.0 |
| 其中恰好是 granule 整数倍的块 | 1,213 | 1,213 | 1,213 | 1,213 |
| 回放：Σ(padded − size) | 0 | 0.02 | 0.07 | **1,219.0** |
| 进程自己的 ledger（冻结前最后一条样本） | 9,933.0 | 12,183.0 | 12,091.0 | 12,183.0 |
| 驱动计数器（冻结态，30 s 稳定） | **11,895.3** | **12,210.9** | **12,211.0** | **12,211.0** |
| 外部 ledger（冻结态，77 个样本全同） | **11,942.00** | **12,258.00** | **12,258.00** | **12,258.00** |
| renderD128 映射字节 | 11,766.2 | 12,082.2 | 12,082.2 | 12,082.2 |
| 相对 0 pad 的差（计数器 / 外部 ledger / renderD128） | — | +315.6 / +316.0 / +316.0 | +315.7 / +316.0 / +316.0 | **+315.7 / +316.0 / +316.0** |

（精确字节：外部 ledger 0 pad 是 `12,522,094,592`，三档非零 pad **都是 `12,853,444,608`**——逐字节相同，比 0 pad 高 `331,350,016 B = 316.000 MiB`。）

**"向上取整到某个固定颗粒"这一族解释在这里整体死掉。** 我先用这张表去找那个颗粒：

| 假设取整颗粒 X | pad 16/64 的预期 | **pad 1 MiB 的预期** |
| --- | --- | --- |
| 4 KiB | 4.8 MiB | 1,219.0 MiB |
| 64 KiB | 76.2 MiB | 1,219.0 MiB |
| **256 KiB** | **304.8 MiB** | 1,219.0 MiB |
| 512 KiB | 609.5 MiB | 1,219.0 MiB |
| 1 MiB | 1,219.0 MiB | 1,219.0 MiB |
| 2 MiB | 2,426.0 MiB | 2,426.0 MiB |

只有 256 KiB 那一档能解释 16/64 的量级（304.8 预期对 315.6 实测，残差 3.6%）——但是：**同一个模型要求 1 MiB pad 至少多花 1,219.0 MiB**（这是个**下界**，不是拟合值：1,219 个活块每个都实打实地多要了 1 MiB，`Σ(padded − size) = 1,278,214,144 B`，任何按请求字节记账的口径都躲不掉），**实测只多了 0.066 MiB。**

于是真相的形状浮出来了：**pad 非零就出现一个 +316.000 MiB 的台阶，然后饱和，不随 pad 长大。**（一条同方向的旁证：hook 日志尾部三笔 `caller=libc10_hip.so+0x41efa` 的返回地址间距，0 pad 时是 4 MiB，三档非零 pad 全是 6 MiB——同样是"有 pad 就变、不随 pad 长大"。）

还有两件事必须记下来，因为它们是后面所有读数的前提：

- **运行中两本账在大幅振荡**：冻结前 8 秒内计数器在 7,595.4–13,055.3 MiB 之间摆，同一时刻成对取样的差在 −1,042 到 +3,540 MiB 之间摆；进程一停，两本账立刻贴到 47 MiB 以内。所以"冻结前的最后一条样本"那一列（9,933.0 / 12,183.0 / …）**不能**和任何冻结态的数直接比——它是撞在振荡相位上的一个快照。
- **`kill -CONT` 会污染日志**：要杀掉被 `SIGSTOP` 的进程得先 `CONT`，那一秒里进程继续跑，日志尾部就混入新记录（原始日志 3,285 次 `hipMalloc`，冻结态只有 2,994）。截断必须用**日志自己的时钟**（第二列是进程内相对秒数），拿 `CLOCK_MONOTONIC` 去过滤会静默地读完整份文件。

**这一轮留下的四个问题**：(a) 计数器多出来的是真内存还是记账假象？(b) 那个"像 256 KiB"的台阶是什么？(c) 为什么 1 MiB pad 不比 16 B 贵？(d) 多出来的到底是谁的内存？

### 第八幕 · 第二轮：把 hook 和 torch 一起摘掉

第一轮戴着 hook、压着 torch，分不清"pad 的贡献"和"hook/torch 自己的贡献"。于是我写了一个**纯 HIP 程序**，按冻结那份日志的操作流逐笔重放：没有 `LD_PRELOAD`、没有 hook、没有 torch，只有 `hipMalloc`/`hipFree`/`hipHostMalloc` + `hipMemGetInfo` + sysfs 读；跑完自己 `SIGSTOP`。四档只差 `--pad`（0 / 16 / 64 / 1 MiB），四次是**同一个二进制**（sha256 `8d3b2b0f8848aec6`）、同一份起始基线。

在跑之前，我先审了一遍这份流到底完不完整（`completeness.py` 逐笔重放五份日志）：

| 日志 | 截断时刻(s) | M | F | H | 未匹配/重复释放 | 重复指针 | 无法解析行 | 末态活表 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `frozen5t0`（0 pad 原次） | 19.923 | 2,994 | 1,775 | 84 | 0 | 0 | 0 | 1,219 / 9,661,579,264 B |
| `frozen5t0b`（0 pad 重跑） | 19.859 | 2,994 | 1,775 | 84 | 0 | 0 | 0 | 同 |
| `frozen5t16` | 19.927 | 2,994 | 1,775 | 84 | 0 | 0 | 0 | 同 |
| `frozen5t64` | 19.887 | 2,994 | 1,775 | 84 | 0 | 0 | 0 | 同 |
| `frozen5t1m` | 19.951 | 2,994 | 1,775 | 84 | 0 | 0 | 0 | 同 |

五次落在同一个活表上，窗口里只出现那三种行。**但这只说明"窗口内一笔不漏"——hook 记的是请求量，不是保留量，也不是驱动的落点。** 这个限度我得一直记着。

四档的结果：

| 项 | pad 0 | pad 16 B | pad 64 B | pad 1 MiB |
| --- | --- | --- | --- | --- |
| `Σ(padded − size)` | 0 | 19,504 | 78,016 | 1,278,214,144 |
| 进程自己的 ledger used | **9,302.0** | **11,728.0** | **11,728.0** | **11,728.0** |
| 驱动计数器（冻结态） | **11,402.0** | **11,718.0** | **11,718.0** | **11,718.0** |
| 外部 ledger used | **11,412.0** | **11,728.0** | **11,728.0** | **11,728.0** |
| 计数器 − ledger | **+2,100.4** | **−9.66** | **−9.67** | **−9.66** |
| 恰好 2 MiB 的映射 | 1,925 | **1** | **1** | **1** |

（精确字节：进程自己的 ledger 在 pad 0 是 `9,753,853,952`，三档非零 pad **都是 `12,297,699,328`**。）

**三条结论，全部精确：**

**一、ledger 的法则逐字节成立：**

```
ledger used = Σ round_up(请求, 2 MiB) + 82.0 MiB
```

pad 0：`9,220.0 + 82.0 = 9,302.0`（实测 9,302.0 ✓）。三档非零 pad：`9,220.0 + 2,426.0 + 82.0 = 11,728.0`（三档实测都是 11,728.0 ✓）。那个 `2,426.0` 是这么来的：1,213 个活块本来就是 granule 整数倍，**加多少 pad 都会被向上取整到下一颗 2 MiB**，每块多记一整颗，合计 2,426.0 MiB——**这就是为什么 16 字节和 1 MiB 的价格完全一样。** 而 `82.0 MiB` 是这个程序不跑任何 kernel 时的底噪。

**顺便，第一轮那个"1 MiB 的请求差额没落到任何账上"的问题在这里结清了：差额一直在账上，只是被按 2 MiB 取整记成了 +2,426.0 MiB。**

**二、事先写死的预言被逐字节命中。** 上面两条法则推出一个可判别的预言：**pad 16 B 和 pad 64 B 必须给出与 pad 1 MiB 完全相同的两列。** 我把它写下来之后才补跑那两档，结果：三档非零 pad 的 own ledger 都是 `12,297,699,328 B`，外部 ledger 三档都是同一个值，恰好 2 MiB 的映射都从 1,925 掉到 **1**。（这是本次追查里唯一一次"先把预言写下来再测"的验证，也是我最愿意拿出来说的一次。）

**三、那个台阶被精确拆开。** 非零 pad 同时干了两件事，而两件我都量到了：

```
Δ计数器 = Δledger + Δ差 = 2,543,845,376 + (−2,212,499,456) = 331,345,920 B = +316.000 MiB
```

- (a) 让 HSA 给每个对齐的活块多记一颗 granule（**ledger +2,426.0 MiB**）；
- (b) **破坏 2 MiB 对齐**，使计数器那一侧约 2.1 GiB 的"无主 2 MiB 映射"整体消失（**差 −2,110.0 MiB**，恰好对应 1,925 → 1 个映射）。

两者相抵，就是那个饱和在 +316 MiB、与 pad 是 16 B 还是 1 MiB 无关的台阶。**§10.4 里那条公式 `计数器 − ledger = 2 MiB × 无主映射 − 21.4` 只是 pad-0 系列内部的规律，跨 pad 不成立**——因为"无主映射"这个量本身在非零 pad 下就不存在了。

最后一条锚（它让后面的结论可以放心地用纯回放去推）：**训练进程与纯回放的差是常数**——外部 ledger 偏移 `555,745,280 B = 530.00 MiB`、renderD128 `432.2 MiB`，四档逐字节相同；计数器偏移在 492.57–492.88 MiB 之间。训练进程多出来的那部分（torch 运行时 + hook 自己）**不随 pad 变化**。

### 第八幕 · 第三轮：写满哨兵，再抢光

前两轮仍然是在**相信 ledger 的数字**。于是这一轮我直接去测内存本身：我写了一个独立程序（同样没有 hook、没有 torch）重放 pad-0 的流，**往每一个分配里写哨兵**（`seed(slot) + i·0x9E3779B97F4A7C15`，写入内核负责重算期望值并统计不匹配字数，`atomicCAS` 记录第一条不匹配的位置），然后按 ledger 自称的 free 精确申请、写满，最后把仍然存活的所有分配**逐字回读**。

| 项 | `sent0`（一次性） | `sentA`（2 MiB 逐块 + 归还） | `sentB`（一次性 + 归还） |
| --- | --- | --- | --- |
| 回放结束时 ledger used / free | 9,452.0 / 6,852.0 | 9,452.0 / 6,852.0 | 9,452.0 / 6,852.0 |
| 申请 / 实得 | 6,852.0 / **6,848.0** | 6,852.0 / **6,842.0**（3,421 块，第 3,422 次失败） | 6,852.0 / **6,846.0** |
| 归还后 ledger | — | **9,452.0 / 6,852.0**（逐字节回到原值） | **9,452.0 / 6,852.0** |
| 归还后计数器 | — | 12,914.6（比抢光前**高** 1,368.0） | 9,434.5（比抢光前**低** 2,112.0） |
| 哨兵写入 / 回读校验字数 | 写入 5,750,915,072 | 回读 1,207,697,408 | 回读 1,207,697,408 |
| 不匹配 | **0** | **0** | **0** |
| GTT / `VmSwap` / 主机 SwapFree | 34.938 / 0 / 全程不变 | 同 | 同 |

两条结果：

**一、ledger 对自己的客户是精确的。** 它说还剩 6,852.0 MiB，就真的把这么多交出来了（扣掉 runtime 自己的开销后是 6,842–6,848 MiB），写满哨兵、零错读回，归还之后**逐字节**回到 `9,452.0 / 6,852.0`。

**二、计数器不跟着回去，而且两条路径方向相反**：一条比抢光前高 1,368.0 MiB，另一条低 2,112.0 MiB。而这两个数**逐个映射**都能对上——一条多了 `+684` 个 2 MiB 映射（684 × 2 = 1,368 ✓），另一条少了 `−1,056` 个（1,056 × 2 = 2,112 ✓）。

我把十一个检查点摆在一起，规律就出来了：

```
驱动计数器 − 自己的 ledger = 2 MiB × (恰好 2 MiB 的映射数 − 活着的 2 MiB 块数) − 21.4 MiB
```

十一个里十个满足，残差稳定在 −21.4/−21.5 MiB（唯一的例外是唯一一次没加落定等待的读数）。**也就是说：计数器高出的那部分，完全由这些 2 MiB 映射解释；而 ledger 从头到尾不认它们。** 设备真被填满时它们就消失（`sentA` 抢光后 4,292 个映射里有 4,290 个是活的 2 MiB 块，无主的只剩 2 个）——**这也是"抢光能超出计数器表面可用量"的原因。**

### 第八幕 · 第四轮：请一个进程里没有 ROCr 的第三方来裁决

第三轮结束时，我面对的是一个**两种解释都说得通**的局面：

- A（HIP/ROCr 进程）声称还剩 6,852.0 MiB，而且**它自己要就真能拿到**——写满哨兵、回读零错；
- 于是要么 **① 驱动计数器虚高**（那部分在硬件上本来就空着，只是驱动算多了），要么 **② ROCr 私吞**（它先前向驱动多要了约 2 GB"备用"，账不算在用户头上；等应用真要内存时它吐出来——**整个过程对驱动透明**，所以 A 自己要当然拿得到）。

**分辨的办法**，是让一个**完全不经过 ROCr** 的进程 B 去要那 6,852.0 MiB：私吞的内存对 B 不可用，虚高的部分对 B 可用。**判据我在测量之前就写死了**（B 自身的开销在两次测量里相减抵消）：

| 假设 | 预言 `M_idle − M_withA` |
| --- | --- |
| ① 计数器虚高（ledger 诚实） | **9.151 GiB** |
| ② 计数器诚实（ROCr 私吞） | **11.235 GiB** |

两者差 2.08 GiB，二值可判。

**为什么选 Vulkan 来当这个裁决者。** HIP 和 A 同栈，不能算独立，排除；ROCm 的 OpenCL（`libamdocl64`）底下仍然是 ROCclr→HSA→ROCr，同样不能算，排除；Mesa 的 rusticl 不经过 ROCr，但本机它的内核编译器是坏的（`clinfo` 编一个最小内核就 `Attribute set does not match Module context!` → `LLVM ERROR: Broken module found` → SIGABRT）；**Vulkan/RADV** 走 libdrm→amdgpu ioctl，与 ROCr 无关，而且**不需要任何着色器或编译器**就能拿显存。核对过的事实：它认出的设备是 `AMD Radeon RX 9070 XT (RADV GFX1201)`；heap1（DEVICE_LOCAL）大小 `17,095,983,104 B` 与 sysfs 的 `mem_info_vis_vram_total` **逐字节相同**；memoryType 3/4 是 `DEVICE_LOCAL|HOST_VISIBLE|HOST_COHERENT`（可以 CPU 直接映射写，实测 5.5 GB/s）。

**独立性用 B 自己的 `/proc/<pid>/maps` 自证**（不是自述）：B 的进程里有 `libvulkan_radeon.so` 和 `libdrm_amdgpu`，**没有** `libhsa-runtime64`、`libamdhip64`、`libamdocl64`；而 A 的进程里 `libhsa-runtime64` 和 `libamdhip64` 各 4 处。

**方法。** 我让 B 分三阶段、每段末尾 `SIGSTOP` 自己：**P0** 只建 instance/device（必须在设备还空着时建好，顺带量出自己的开销）；**P1** 先按"定值探针"精确申请 A 的 `ledger_free`，再用降阶梯（1 GiB → 256 → 64 → 16 → 4 → 2 → 1 MiB）反复申请到失败，每块立刻写满哨兵；**P2** 全量回读（走 staging 拷贝，实测约 6.5 GB/s；BAR 直读只有约 10 MB/s）。**每块是否算数只看正面证据**：计数器增量 ≈ 申请量（±256 KiB）且 GTT 不动，否则释放该块并降档。两侧哨兵常数不同（A 用 `0x9E3779B97F4A7C15`，B 用 `0xD1B54A32D192ED03`），**一旦串写，从数据本身就能指认是谁的。**

三次运行：`base3` = B 单独；`r0` = A 单独（同 session 参照）；`dec0` = 决定性的一次——B 停在 P0 → A 回放并冻结 → **30 秒无人触碰的保持观测** → B 抢 → A 复起再抢 → 双方全量回读。

| 检查点 | A 的 ledger used / free | 驱动 vis | 驱动 gtt | B 实得 |
| --- | --- | --- | --- | --- |
| `base3` B 单独 | — | 17,086,889,984 | 283,975,680 | **17,011,048,448 B（15.843 GiB）** |
| `r0` A 回放后 | 9,911,140,352 / **7,184,842,752** | 12,107,448,320 | 21,889,024 | — |
| `r0` A 抢完 | 17,095,983,104 / 0 | 17,077,714,944 | 21,889,024（**没动**） | — |
| `dec0` a1（A 冻结） | 9,911,140,352 / **7,184,842,752** | **12,138,266,624** | 290,328,576 | — |
| `dec0` a1 + 30 s | 同 | 12,138,307,584 → **12,138,266,624** | → 290,328,576 | — |
| `dec0` b1（B 抢完） | 同（**没变**） | **17,087,578,112** | 290,328,576 | **4,949,278,720 B（4.609 GiB）** |
| `dec0` a2（A 再抢） | 17,095,983,104 / 0 | 17,086,160,896 | **5,231,304,704** | — |

（`dec0` 里 B 的降阶梯：1 GiB **第 1 次就被拒** → 256 MiB ×2 → 64 ×1 → 16 ×2 → 4 MiB ×2 → 2 MiB ×1 → 1 MiB ×6，共 18 块 = 4,609.0 MiB，全部通过正面证据检验；另有 7 次被判为"落进主机内存"而释放。）

**判定：**

| | 值 |
| --- | --- |
| `M_idle`（B 单独能拿到） | 17,011,048,448 B = 15.843 GiB |
| `M_withA`（A 冻结时 B 实得） | **4,949,278,720 B = 4.609 GiB** |
| `M_idle − M_withA` | **12,061,769,728 B = 11.235 GiB** |
| 假设 ① 预言 | 9,825,157,120 B = 9.151 GiB → **差 2,083 GiB**（错） |
| 假设 ② 预言 | 12,062,609,408 B = 11.235 GiB → **差 839,680 B = 0.007%**（中） |

**结论：驱动计数器是诚实的，ROCr 真的握着约 2.07 GiB 的驱动级显存，而它自己的 ledger 不承认这笔账。** 换成人话：**HIP 说还剩 6,852.0 MiB，外人只拿到 4,720.0 MiB，中间 2,132.0 MiB 是 ROCr 的私房钱。**（第三方跑完之后计数器停在 `17,087,578,112 / 17,095,983,104`——**只剩 8.0 MiB**。）

还有三条附带结论，每一条单独看都值得写下来：

1. **那 2.07 GiB 是稳定持有，不是记账迟滞。** 30 秒保持观测里计数器只动了 40,960 B、GTT 只动 45,056 B。
2. **ROCr 能把这份储备回收给自己的客户。** `r0` 里 A 一次拿到全部的 7,184,842,752 B，而计数器只涨了 4,970,266,624 B、GTT 一动不动——其中 2,112.0 MiB 就是从 ROCr 自己的储备里出来的。所以"ledger 的 free 是真的"这句话，**对 ROCr 的客户成立，对别人不成立。**
3. **显存真的不够时，ROCr 拿主机内存顶上，而且不说。** `dec0` 里 B 拿走 4.95 GiB 之后，A **仍然一次拿到了全部的 7,184,842,752 B**——计数器不动（−1,417,216 B），而 **GTT 从 290,328,576 涨到 5,231,304,704（+4.94 GiB）**，回读零错，而 `hipMemGetInfo` 全程把它报成显存。**这里没有报错，只有一段静默的替换。**

（另外两个交叉验证：裸 C 的 HIP 读数器站在计数器那一边——冻结态它报 `used 11.293 GiB / free 4.629 GiB`，与第三方实际拿到的差 21 MiB 以内；而 B 抢走 4.95 GiB 之后它的数字**一点都不动**，说明 HIP 的 free 看不见别的 API 的分配。以及：两边的哨兵常数不同，双方各自回读自己的内存零错，**所以 A 的 7.18 GB 和 B 的 4.95 GB 不是同一批页。没有别名。**）

### 第八幕 · 第五轮：把"无主映射"物化成对象

前四轮量的都是**账**；最后一轮我干脆去量**对象本身**——四份 `amdgpu_vm_info` dump，逐进程列出每个 BO 的大小和状态。

| | 0 pad | 16 pad | 64 pad | 1 MiB pad |
| --- | --- | --- | --- | --- |
| trainer VM 的 pid | 100391 | 101237 | 102083 | 103108 |
| BO 个数 | **3,618** | 2,477 | 2,487 | 2,493 |
| BO 字节 | 12.267 GiB | 12.576 GiB | 12.576 GiB | 12.576 GiB |
| 其中 VRAM | 12.260 GiB | 12.568 GiB | 12.568 GiB | 12.568 GiB |
| `Kernel PT/PDs`（4 KiB BO） | 1,086 = 4.24 MiB | 1,000 = 3.91 MiB | 1,010 = 3.95 MiB | 1,016 = 3.97 MiB |
| **恰好 2 MiB 的 BO** | **1,926**（= 3,852 MiB） | **2** | **2** | **2** |
| 恰好 4 MiB 的 BO | 不在主列表 | **872**（= 3,488 MiB） | 872 | 872 |

这四条结论把第一轮留下的四个问题全部关掉了：

1. **不是页表。** `Kernel PT/PDs` 在每个 pad 上都是 3.9–4.2 MiB——比那 2.1 GiB 小三个数量级。
2. **那些"无主 2 MiB 映射"是一池真实的 2 MiB BO。** pad 0 有 **1,926** 个恰好 2 MiB 的 BO，加 pad 的运行只有 **2** 个。差值可以拆成约 869 个"活着的、正好 2 MiB 的块"（hook 活表自己数的）加上**约 1,055 个不属于任何活分配的 BO**——`1,055 × 2 MiB = 2,110 MiB`，正好对上第四轮里 ROCr 交还给自己客户的那 2,112.0 MiB（而且这 1,055 和第三轮从地址空间独立数出来的 1,058 是同一条线）。
3. **加 pad 的运行没有池子，而且它的尺寸直方图带着 pad 的指纹**：每一个对齐的尺寸类**整体上移一颗 granule**（2→4、14→16、20→22、26→28 MiB），池子消失。**pad 干的事，是把一池可回收的 ~2.1 GiB 换成 ~2.4 GiB 永久挂在活块上的 granule。**
4. **BO 总量独立复现了计数器的差**：12.267 对 12.576 GiB = **+316 MiB**，而计数器给的是 +315.66（训练进程）/ +316.000（纯回放）。两个不共享任何代码的仪器吻合到 1 MiB 以内。（一条没解释的：BO 总量在每个 pad 上都比计数器高约 660 MiB——常数，相减会抵消。）

### 第八幕的答案

我把三本账摆在一起（同一份冻结的活表：1,219 块 / 9,214.0 MiB）：

| 仪器 | 0 pad | 加 pad | 差 |
| --- | --- | --- | --- |
| HIP ledger（它的客户还能要到多少） | 9,302.0 used / 7,002.0 free | 11,728.0 used / 4,576.0 free | **+2,426.0 / −2,426.0 MiB** |
| 驱动计数器（真显存，第四轮证明它诚实） | 11,402.0 | 11,718.0 | **+316.0 MiB** |
| BO dump（对象本身） | 12,267 MiB | 12,576 MiB | **+316–317 MiB** |

**它们不矛盾。** 因为 pad 和 pool 是同一笔 granule 级开销的两种花法：

- **不加 pad 时**，活块自己不占额外 granule，但 ROCr 留着**约 1,055 个 2 MiB BO（2,110 MiB）当池子**——驱动把它算作已用，而 ROCr 随要随给。于是这个进程真正能用的是 `4,902 MiB 设备空闲 + 2,114 MiB 池子 ≈ 7,016 MiB`，对上它自己 ledger 里的 7,002.0 MiB。
- **加 pad 时**，约 1,213 个对齐活块每块永久拥有一颗额外的 granule（**+2,426 MiB**），池子消失，于是能用就是设备空闲：`16,304 − 11,718 = 4,586 MiB`，对上 ledger 的 4,576.0 MiB。
- 设备层面的净差 = `2,426 − 2,110 = 316 MiB`，正是计数器和 BO 总量报出来的那个数。

**所以对 ROCr 自己的客户（也就是 trainer）来说，pad 花掉的是完整的 2,426.0 MiB（2.37 GiB）可用内存，而不是计数器显示的 316 MiB。** §10.3 的 +2,534 MiB 是同一个现象在 run 峰值（1,255 个活块，checkpoint 保存那一刻）上的测量。

两条要带走的结论：

- **`hipMemGetInfo` 判不了"还剩多少余量"。** 对自己乐观约 2.1 GiB（池子既记在驱动账上、又还能交出来）；对外人则偏 2.1 GiB 的另一个方向（第四轮：外人只拿到 4,720.0 MiB，而 ledger 广告 6,852.0 MiB）。
- **显存耗尽不会给你一个失败，它会给你主机内存。**（第四轮 `dec0`：卡满了，`hipMalloc` 照样成功，差量静默落进 GTT。）

## 第九幕 · 路线一：自己写分配器

> 证据：[`../amdfq.md`](../../amdfq.md) §12

第七幕留下的话是"机制成立、设计不合格"。我最直接的想法，就是把 pad 的原理**接管到自己手里**：既然 pad 之所以贵，是因为 runtime 给每个块单独多买一颗 granule，那就自己用 VMM API（`hipMemAddressReserve`/`hipMemCreate`/`hipMemMap`/`hipMemSetAccess`）划一大片地址空间，自己切块，然后在**每块后面映射同一个共享的 pad granule**——于是整个进程的 slack 只花一颗 granule，而不是 1,255 颗。

**它做到了两件事**：成本降了下来（整个进程只花一颗 granule），而且**它确实消掉了 step-10 fault**。

**然后它用五种互不相同的方式把进程搞坏了。** 出问题的不是那个 fault，而是别的东西：两个不相关的 kernel 抛非法 shader 指令、wave 的 PC 跑到未映射地址、野指针、某一步的 loss 变成 NaN。五种，没有一种被解释。

**我至少把它排除了两半**（这一步比失败本身更有价值）：

- **不是 VMM 调用本身有害。** 我做了一个 shadow 模式（`AMDFQ_VMM_SHADOW=512`）：把每一笔真实分配镜像到一片没人读写的 VMM 内存上，走完同样的 `hipMemAddressReserve`/`hipMemMap`/`hipMemSetAccess` 序列，**不服务任何操作数**。进程干净。顺带说，那个 shadow 里的每一页也都是**同一个共享对象**的映射——这为路线二埋了伏笔。
- **也不是切地址空间的方式。** 我换成 per-allocation 布局（每笔分配自己 reserve、自己 free，不要 arena 和 free list），照样崩。
- **而且对照组是健康的**：同一份配置、`AMDFQ_VMM=0`（什么都不服务）的那次跑到 **step 66**，损失 0.0862 / 0.0528 / 0.1023 / 0.0067 / 0.1074——一路上没有任何异常。

所以我得出的结论是：**"VMM 调用有害"被排除；真正致命的是"把操作数本身建成 VMM 内存"。** 一个由我自己的分配器交出去、被 kernel 当作操作数来读的内存，不知道什么原因会破坏进程的其它状态——那是一个至今没有解释的现象，但它的形状更像是"进程自身状态被随机破坏"，而不是"kernel 有缺陷"。

路线一就此封存（**研究价值保留**：一个能让两个不相关的 kernel 抛非法指令、让 GPU 飞向野指针、让 loss 变 NaN 的分配器，不是一个已经讲完的故事）。

## 第十幕 · 路线二：尾部守卫

> 证据：[`../amdfq.md`](../../amdfq.md) §13，代码在 [`../amdfq/amdfq_tail.c`](../amdfq_tail.c)

路线一的问题不是"VMM"，而是"用它来当分配器"。于是路线二只改了这一个维度：**让 `hipMalloc` 继续分配，我只在它后面做加法。**

整个思路分四步：

1. `hipMalloc` 返回之后，取这块的 extent（用 runtime 自己的 `hipMemGetAddressRange`，再按 granule 向上取整）。
2. 问一个问题：**extent 之后那 16 字节所在的那一页，有没有东西映射着？** 如果 `hipMemGetAddressRange` 说它落在另一个活分配里，那读到这里本来就不可能掉出任何东西——**什么都不用做**。
3. 如果没有任何东西映射着（也就是会 fault 的那种情况），就用 `hipMemAddressReserve` 拿那一页——**hint 必须正好落在那里，否则不算**——然后把**一个共享对象**（进程启动时 `hipMemCreate` 一次）映射进去（`hipMemMap` + `hipMemSetAccess`）。
4. `hipFree` 时先卸掉这块自己的守卫，然后**再问一遍**：刚消失的这块，是不是前一块的守卫？是的话，前一块（还活着）现在需要一页新的。

**为什么必须是"同一个"对象**——这条是设计约束，不是整洁癖：**runtime 会把每一个 `hipMemCreate` 对象都记成 2 MiB 显存**，哪怕对象背后只有 4 KiB。一块一个对象，就会让 `hipMemGetInfo` 每块涨 2 MiB 而实际几乎没用什么——那就把省下来的又花回去了。

**hint 落不到目标页怎么办？**（实测约 0.2%，实际上就是 runtime 自己预留下的那片地址空间）**我把这块还回去，按 `size + 16` 重新申请一遍**——也就是退回第七幕的 pad，把它当作这条路径的兜底。贵，但只贵在 0.2% 的分配上。

### 10.1 它值多少

探针（`vmm_probe.c`）：

| | 第七幕的 pad-16 | 路线二，一个共享守卫 |
| --- | --- | --- |
| 1,000 个 2 MiB 块的显存 | 4,000 MiB | **2,014 MiB**（1,000 块 + 那一个共享守卫） |
| 400 个被保护的块 | — | **总共 +1.6 MiB** |
| 12,000 个被保护的页 | — | **总共 4 MiB** |
| 一次分配 / 一次释放 | 7.6 µs / 15.2 µs | 18.6 µs / 15.2 µs |

真跑（2026-09-17，240 秒，与 pad-16 那次**同一段分配序列**）到了 **step 150**，112,688 次分配；取同一个活块集合对比：

| （MiB） | pad 16 | 尾部守卫 | 差 |
| --- | --- | --- | --- |
| 取样时活块数 | 856 | 856 | — |
| `gran` = Σ round_up(请求, 2 MiB) | 7,466 | 7,466 | 0 |
| `rgran` = Σ round_up(runtime extent, 2 MiB) | 9,166 | **7,468** | **−1,698** |
| runtime 自己的 ledger | 9,799 | **8,103** | **−1,696** |
| 驱动计数器 | 9,787 | 10,178 | **+391** |
| 计数器 − ledger | −12 | **+2,075** | — |

**最后两行就是那个陷阱**，也是第八幕的价值所在：同一个活块集合下，尾部守卫那次的**计数器反而高 391 MiB**，乍看像"守卫一点都不省"。但第八幕说过为什么——**不花 granule 的运行，会保留一池驱动已记账、却还能回收的内存**（这里 `计数器 − ledger = +2,075 MiB`；`base` 是 +2,454，pad-16 是 −12）。守卫自己的物理成本就是 `rgran` 超出 `gran` 的那 2 MiB（一个共享对象）。

**我差点就按那张表的最后一行把它判死了。** 具体地说，我一度得出过"路线二只赢了约 100 MiB"的结论——因为当时对比的是两个**都已经顶到天花板**的运行，谁也看不出差别。若不是第八幕把那 2.1 GiB 的池子查清楚，我险些把这个方案当成没用的东西丢掉。

那次运行留下的心跳行是这样的：56,000 次分配被检查，**55,902 页被保护**（99.8%）、54,919 页被释放、983 页当前活着、**98 次走了 pad 兜底（0.18%）**，reserve / map / unmap 失败各 0 次。

### 10.2 值多少，一句话

| 口径 | 相对第七幕的 pad-16 省下 |
| --- | --- |
| 每 1,000 个块（探针） | **1,986 MiB**（4,000 → 2,014） |
| 尾部守卫那次运行在 856 个活块上 | **1,698 MiB**（`rgran` 9,166 → 7,468；ledger 9,799 → 8,103） |
| step-5 那 1,213 个对齐活块（第八幕的 ledger 法则，四档 pad 逐字节验证过） | **2,426.0 MiB** |

而它是真的 VRAM，不是记账把戏——第八幕数过对象：pad 的 granule 是 trainer VM 里真实的 BO（872 × 2 MiB 变成 872 × 4 MiB，其它对齐尺寸类整体上移一颗），而不加 pad 的账上留着的那 ~2.1 GiB 是**约 1,055 个真实的 2 MiB BO**（对驱动是真的，随要随还给它自己的客户，别人碰不到）。

**路线二同时也回答了那个悬而未决的问题**：§12 曾经问"破坏路线一的是 VMM 调用本身，还是用 VMM 内存当操作数？"——路线二跑了 150 步、99.8% 的分配都有一位守卫，进程一路健康。**所以 VMM 调用和大规模映射共享对象都是无害的；搞坏路线一的是把操作数本身建在 VMM 内存上。**

### 10.3 它现在是默认行为

`amdfq/amdfq_tail.c` 就是上面那四步，**默认开启**。第七幕的 pad 退居兜底（0.2%）。`AMDFQ_TAIL=0` 关掉守卫、变回纯转发，用来复现最初那个 step-10 fault——**换句话说，我把这个 bug 的复现开关做成了补丁的一个环境变量。**

（仓库的 `start_train.sh` **不**自动 preload 它；要用就显式带上。这是刻意的：一个会改变内存布局的东西，不该在没人知道的情况下生效。）

## 尾声 · 还没关掉的账

一份诚实的结尾应该把没解决的部分也列出来。

**一、到底有多少 kernel 会这样读超，我不知道。** 影响面是 1,830 个可以发射的 bf16 kernel × 10 个形状 = 18,300 个作业，这份清单已经生成好了（`fixes/hip1/resources/bf16-overrun-jobs.tsv`），但**全量扫描我没有跑**（计划里那一步叫 M4，仍然开着）。原因是我把成本估错了：大头不是发射本身，而是**每次 fault 之后 ROCr 要花约 7 秒复位设备**——按 fix3 那个 fault 率，全部跑完是几个小时。所以现在能说的是"这些 kernel 里有会读超的"，而不是"有百分之多少会"。同样，前面所有的"读是惰性的"证据都成立于那些运行里真正执行过的 kernel，不是全部 1,830 个。

**二、fault 响应本身会失效——而且是以一种会让实验悄悄作废的方式。** 2026-09-16 那天，从 16:45 到 17:58 之间某一刻起，**每一次访问未映射显存都不再产生页错误杀进程**：GPU 100% 忙、进程在 `hipStreamSynchronize` 里永远自旋（`State: R`、`wchan: 0`、`voluntary_ctxt_switches` 恒为 3，是用户态轮询不是阻塞）、内核日志**一行都没有**。四个不同程序、两条独立进入 hipBLASLt 的路线，全部如此；而那些**不**触碰未映射页的形状，crc 一如既往。重启之后恢复——但那次重启同时把内核从 `7.2.4-zen2-1` 升到了 `7.2.6-zen2-1`，所以"状态被清了"和"驱动换了个 build"这两件事没有被分开。（那一次的证据现在拿不到了：当时没有挂探针，重启把状态清掉了。）

为什么这件事对我很重要：**所有缓解措施的评价都建立在"fault 还会被报出来"这个前提上**。一个卡住的状态会让"这次没崩"看起来像"这次没越界"。所以长跑之前先打一发 canary（`fixes/hip1/repro_standalone.sh`）：它会崩就说明通路健康，它挂住就说明机器在这个状态里——然后按 `gfx1201-fault-response-wedge.md` §4.2 的判定表，用探针计数去指认层：`gmc` 计数为 0 → GPU/固件压根没上报；`gmc` 有但 KFD 的 evict/restore 不再推进 → KFD 的状态机；两者都正常而进程始终没被通知 → 通知路径。

**三、那 ~2.1 GiB 的池子到底是干什么用的，我没有查清。** 我知道它是约 1,055 个真实的 2 MiB BO，知道 ROCr 会把它交还给自己客户，知道第三方拿不到——但我不知道 ROCr 为什么留着它、留多少的策略是什么。在 16 GB 的卡上，那是**别人借不到、而 ROCr 自己用不完**的余量。

**四、几条小账。** BO 总量在每个 pad 上都比计数器高约 660 MiB（常数，相减抵消，没解释）；一次性抢光的边界有 ±2 MiB 的跑间抖动（起点逐字节相同）；逐块释放之后池子留下 684 个映射、一次性释放之后是 −1,056（池子被清空且没重建）——这个不对称没有验证。

**最后一句。** 我最终交付的东西，不是一个"修好了"的故事。**我没能让 AMD 的 kernel 变对，也没能让 ROCm 的内存管理变对；我做的是在两者之间放了一块内存，让那次越界读有地方落。** 代价是每进程一颗 granule，收益是大约 2 GiB 的真实显存，和一遍能跑到 step 150 的训练。

如果哪天 AMD 从架构层给出了那个"尾部一定合法"的保证，这个补丁就可以删掉了——**而我会很乐意删掉它。**
